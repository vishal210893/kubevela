The Application controller, explained

What happens between kubectl apply -f app.yaml and a running, self-healing deployment. Each claim links to a file:line in this repo. Skim the diagrams first, open the folded tables when you need detail.

1ParseThe spec and its X-Definitions become an in-memory Appfile.
2SnapshotThe Appfile is hashed and stored as an immutable ApplicationRevision.
3PlanWorkflow steps become runners. The controller hands the engine a set of callbacks.
4ExecuteThe engine runs the steps. Each apply-component step calls back in, renders CUE, and applies the result.
5TrackEvery object is recorded in a ResourceTracker before it is applied. The tracker is the inventory.
6SettleHealth checks, drift correction, garbage collection, status write. Repeat every 5 minutes.

01Big picture

The controller is a render-and-apply pipeline wrapped in a workflow engine. One detail makes it unusual: it does not own child resources through ownerReferences. It records them in cluster-scoped ResourceTracker objects instead, and everything (deletion, drift repair, GC) works off that record.

02How a reconcile starts

Before the controller: two webhooks

Every create or update passes admission first. The mutating webhook stamps the requesting user into annotations, generates workflow step names, and assigns a shard. The validating webhook rejects bad components, bad workflows, and definition access the user lacks. The reconciler can assume a defaulted, valid object.

webhook/.../mutating_handler.go:102validating_handler.go:66validation.go:92

Three things wake the controller

  • Application events. A predicate drops updates that only touched workflow status, so the engine's own writes don't cause storms. Generation changes always pass. So do pure resyncs, and that resync is what drives self-healing. application_controller.go:673
  • ResourceTracker deletions. Deleting a tracker re-enqueues its app (found by labels). Other tracker changes are ignored by default. application_controller.go:816
  • PolicyDefinition changes. These only refresh the in-memory policy index and cache. No reconcile is queued. application_controller.go:792

Entry guards, in order

  • Fetch the app. If it's gone, there is nothing to do. controller:116
  • Skip apps that are paused, or addressed to a different controller version. controller:126, :130
  • Load the app's resource trackers and resource policies up front, so every later decision works from one consistent view. apply.go:78 resourcekeeper.go:147
  • Sort out the finalizer. A brand-new app just gets one and the pass ends. A deleting app runs garbage collection until every tracker and revision is gone, checking back every 3 seconds while resources drain. controller:486
Trackers are cluster-scoped, so a namespaced app cannot own them. That is the whole reason the finalizer exists, and why a stuck child resource blocks app deletion.

1

Policy transforms

Platform teams can install policies that rewrite every application before it deploys: inject labels, force settings, adjust the spec. Those rewrites happen first, in memory, so the rest of the pass only ever sees the transformed app. Rendering policies is expensive, so results are cached for a minute and reused while nothing has changed.

application_policies.go:67application_policy_cache.go:90policy_scope_index.go:61
2

Parse the spec

An Application spec is mostly names and properties. The actual logic lives in definitions: reusable templates that say how a "webservice" or a "gateway" becomes real Kubernetes objects. This step looks up every definition the app uses and bundles everything into one in-memory structure the rest of the pass works from. Apps pinned with a publishVersion annotation skip the live spec and use their stored snapshot instead, so nothing moves until the pin does.

parser.go:87template.go:74parser.go:96 (publishVersion)
3

Snapshot a revision

The spec, together with every definition it uses, is frozen into a numbered snapshot. That snapshot is what makes rollback, replay, and pinning possible: even if someone edits a definition tomorrow, this deployment keeps rendering from the copy it shipped with. Snapshots are compared by hash, so applying the same spec twice does not create a new version.

revision.go:86revision.go:497revision.go:556
4

Apply policy resources

Some policies are pure configuration (where to deploy, what to skip during cleanup) and were already absorbed in earlier steps. Others produce actual Kubernetes objects, and those objects get applied to the cluster here, before any component does.

apply.go:469appfile.go:198
5

Decide whether to deploy again, then plan the workflow

A finished workflow doesn't rerun on every pass. It runs again only when something meaningful moved: the app changed (new revision), someone asked for a restart, or, for helm charts, the contents of a referenced ConfigMap or Secret changed, even though the spec itself didn't. Then the deployment plan is built: each workflow step becomes a runnable unit, and the controller hands the engine the hooks it will need to render, apply, and health-check components.

workflow.go:104valuesfrom_fingerprint.go:100generator.go:70
6

Run the workflow

The workflow engine takes over and walks through the steps: deploy this component, wait for that one, pause for approval. A deployment usually spans many reconcile passes; each pass advances the workflow a little and comes back at the engine's backoff. Still going means come back later. Failed means stop and say so. Succeeded means move on to settling. Section 4 shows what one step actually does.

controller:231 (execute)controller:280 (state switch)
7

Settle: health, late traits, drift, cleanup

Once the workflow succeeds, the controller takes stock. It asks each component whether it is actually healthy, and that answer decides the app's phase: running or unhealthy. Traits that need a live, healthy workload to exist (a monitoring sidecar that reads real replica counts, say) are applied only now. Anything that drifted from what was deployed gets put back. And anything left over from older versions gets deleted.

controller:910 (health)apply.go:524 (post-dispatch)statekeep.go:41gc.go:112
8

Write status, schedule the next pass

The pass ends by recording what happened on the app's status, and only if something actually changed. Then the controller books its own next visit: 5 minutes by default, or whatever interval the app asks for (10 seconds at the fastest). That periodic revisit is the heartbeat behind drift repair and self-healing.

controller:556vars.go:30 (5 min)application_metrics.go:39

Three things worth knowing about this path

  • Record first, apply second. The tracker write happens before the cluster write. If the controller dies between the two, GC can still find the resource. dispatch.go:84
  • Healthy components can still re-apply. The dispatcher re-applies when component properties differ from the revision, or when the autoUpdate annotation is set. dispatcher.go:167
  • Writes are three-way merge, not server-side apply. The applicator diffs desired, live, and a last-applied annotation, like kubectl apply. Ownership, shared, read-only, and take-over policies are enforced here as apply options. utils/apply/apply.go:185

How health is decided

Health is not guessed from pod counts. Every definition can ship a healthPolicy: a CUE expression evaluated against the live object that the controller reads back from the cluster. The rules:

  • No health policy means healthy. A definition without healthPolicy reports healthy as soon as its resource applies. If a component looks "instantly healthy", this is usually why. health/health.go:52
  • A component is healthy when its workload and all of its traits are healthy. One sick trait marks the whole component, and one sick component marks the whole app unhealthy. apply.go:325 controller:644
  • Held-back traits don't count against health. A PostDispatch trait that hasn't applied yet shows as "pending" in status and is excluded from the verdict, otherwise the app could never become healthy enough to apply it. apply.go:393
  • Terraform components are special. Their health comes from the Configuration object's state field, not from CUE. apply.go:281
  • The same CUE machinery also fills status.services[].message from the definition's customStatus expression, so the message you see in vela status is authored by the definition, not the controller. appfile.go:115

What holds state between passes

  • The current ResourceTracker holds every dispatched object, with raw manifest data for drift repair. It is the inventory the controller trusts. resourcekeeper.go:135
  • The root tracker holds resources whose GC policy says they outlive revisions. dispatch.go:107
  • The workflow's own progress lives on the app's status and seeds the next pass. The engine itself remembers nothing between reconciles. generator.go:134
  • Running totals. Service health and the list of applied resources accumulate while the workflow runs, then merge into status. Once the workflow finishes, the applied list is rebuilt from the tracker, which wins any disagreement. controller:244, :323

07Trackers and cleanup

ResourceTrackers replace owner references in KubeVela, so understanding them explains most of the lifecycle behavior: why deletes work across clusters, why drift gets repaired, and where old resources go.

An app owns up to four kinds of tracker

Each entry in a tracker stores the object's identity (cluster, kind, name, namespace, which component created it) plus, normally, a full copy of the manifest as applied. That copy is what drift repair re-applies later. Under apply-once, only the identity is stored, which is exactly why apply-once disables drift repair.

resourcetracker_types.go:129 (ManagedResource)dispatch.go:62 (meta-only under apply-once)

How cleanup actually runs

Garbage collection is a mark-and-sweep over history trackers, run at the end of every settled pass:

  • Mark. History trackers are declared inactive and given a deletion timestamp. On a deleting app, every tracker is marked, including current and root. gc.go:249
  • Sweep. Each marked tracker's resources are checked: a resource still claimed by a newer tracker is left alone, everything else is deleted. Deletion respects dependencies (dependents go first) and shared resources are handed over to the next sharer instead of deleted. gc.go:286 gc.go:358
  • Finalize. Once a tracker holds nothing live, its finalizer drops and it disappears. While anything is still draining, the app shows a Deleting condition naming what it's waiting for, and the pass retries every 3 seconds. gc.go:451 controller:417
  • Legacy mode is throttled. For apps not deleted, the deep "is anything orphaned" scan runs on roughly 1 pass in 10, to keep steady-state reconciles cheap. gc.go:55 (MarkWithProbability 0.1)
  • Revisions are trimmed too. Old ApplicationRevisions beyond the limit (10 by default, tunable per app through the garbage-collect policy) are deleted, oldest first, never the one in use. gc_rev.go:59
A useful mental model: the current tracker is the contract. Dispatch writes the contract, drift repair enforces it, GC deletes whatever fell out of it, and app deletion is just "shrink the contract to nothing, then let go".

08Clusters and identity

Two invisible properties ride along with every apply: which cluster it goes to, and who it acts as. Both are decided long before the write happens.

  • The cluster travels on the manifest. When a component is assembled, its target cluster is stamped onto each object. At write time that stamp becomes a routed request through the cluster gateway. The hub never talks to managed clusters directly; the gateway proxies everything. generator.go:470 dispatch.go:145
  • Topology decides the targets. A topology policy turns one component into one apply per target cluster, each with its own health check. The deploy workflow step fans these out.
  • Some traits refuse to leave home. A trait marked control-plane-only always lands on the hub, even when its component goes to a managed cluster. Useful for things like hub-side DNS records. generator.go:364
  • Writes impersonate the creator. The mutating webhook recorded who created the app. Every apply and health read runs as that identity, so RBAC is enforced per user, not per controller. When a reconcile hits a Forbidden error, check the creator's permissions, not the controller's. userinfo.go:45
  • Cluster version is visible to templates. Definitions can branch on the target cluster's Kubernetes version through context.clusterVersion, which is how one definition supports clusters running different versions. process/handle.go:105

09Errors and requeues

  • Failures before the workflow (parse, revision, policy) all exit the same way: set an error condition, write status, return an error so controller-runtime backs off and retries. controller:530
  • A workflow that fails is not an error. It is a normal branch: finish the workflow, GC, write status. An error from the engine is different and uses the backoff path. controller:298 vs :238
  • Health check errors don't fail the pass. They are logged and the app just stays unhealthy. controller:932

Self-healing is periodic, not event-driven. Nothing watches your Deployments. Drift gets fixed when the resync runs StateKeep, which is why the event filter deliberately lets no-change resync events through.

10Where to extend

  • Definitions are the front door. Component, Trait, Policy, and WorkflowStep definitions are CUE templates. New capability, no controller change. template.go:74
  • Trait stages. spec.stage: PreDispatch or PostDispatch moves a trait to a different wave. PostDispatch traits can read the live workload as context.output. dispatcher.go:241 apply.go:569
  • Trait flags. manageWorkload lets a trait own the workload (the controller stops applying it). controlPlaneOnly pins the trait's output to the hub cluster. generator.go:511, :364
  • Resource policies (apply-once, garbage-collect, shared-resource, take-over, read-only, resource-update) become apply options at write time. dispatch.go:147
  • Annotations and feature gates change behavior without code. Both are listed in full in section 11.
  • Custom workflow steps. Step providers receive the controller's apply, render, and health hooks through a single params object, so a new step type never has to import controller internals. generator.go:86

12Debugging guide

Things that surprise people

  • Editing a child Deployment does nothing until the next resync. Nothing watches workloads.
  • Editing a definition does nothing to running apps. Definitions are pinned in the revision. parser.go:685
  • Manual edits to managed resources get reverted by StateKeep. Use an apply-once rule if that's not what you want.
  • RBAC errors during reconcile usually belong to the app's creator, not the controller. Identity is impersonated from annotations. userinfo.go:45
  • An app stuck in deleting means a tracker still has resources. Check kubectl get resourcetrackers -l app.oam.dev/name=NAME and the Deleting condition message.
  • A paused or version-mismatched app exits before any status write, so its status looks frozen. controller:126
  • A just-edited global policy can take up to a minute to apply. Rendered policies are cached. application_policy_cache.go:90
  • A component with no healthPolicy reports healthy the moment it applies, which can make a broken deployment look green. health/health.go:52

Breakpoints that pay off

  • controller:113 reconcile entry. The trace tags frame every log line.
  • parser.go:94 is rendering pinned to a revision?
  • revision.go:113 why did (or didn't) a new revision get created?
  • generator.go:316 start of a component apply: comp, cluster, namespace.
  • appfile.go:599 CUE output. First stop for render errors.
  • dispatcher.go:167 why was a healthy component re-applied (or not)?
  • dispatch.go:88 the line between bookkeeping and cluster writes.
  • statekeep.go:105 who keeps overwriting my object.
  • gc.go:136 GC entry, for stuck deletions.
  • controller:560 the status diff gate. Explains "my status didn't update".
