# Unify HTTP and OCI Add-on Chart Registries

## Recommendation

Replace the separate `ociRegistry` implementation with one Helm-chart registry façade whose backend is selected from the repository URL. An `http://` or `https://` URL uses the indexed Helm-repository backend; an `oci://` URL uses the OCI backend. Keep OCI-only mechanics—tag enumeration, registry-client pull/push, portable catalog discovery, and catalog publication—inside that backend.

“Done” means every consumer resolves a chart-backed add-on through one construction path and one shared package-loading implementation, while existing `{"oci": ...}` registry records and `--type oci` commands continue to work during a deprecation window. Git, Gitee, GitLab, OSS, local installation, rendering, and the add-on component contract remain unchanged.

<Callout id="decision" tone="decision">

**Proceed with a façade plus two transport backends.** The duplication is real at the `VersionedRegistry` method and chart-decoding layers. The OCI catalog and registry-client operations are not duplication; they compensate for capabilities an HTTP Helm repository gets from `index.yaml`.

</Callout>

### Scope and non-goals

This plan is grounded in all source and test files under `pkg/addon`, the registry and push CLI, the CueX add-on provider, the render-only service, the compatibility webhook, the generated ComponentDefinition, the add-on component e2e, and Helm 3.14.4's local implementation.

In scope: registry construction, configuration normalization, credentials, chart listing/resolution/pull, push routing, cache/install/helper branches, backward compatibility, and tests.

Out of scope: changing the add-on package format; changing Git/OSS readers; redesigning the add-on component CUE API; removing OCI catalog support; changing the chart component's separate `repoType: oci`; or silently standardizing prerelease semantics during the structural refactor.

### Add-on lifecycle

**Imperative enable.** `EnableAddon` creates an `Installer`; `loadInstallPackage` resolves either a version-capable chart registry or an `AsyncReader` source. The installer validates package/system requirements, resolves and installs dependencies across registries, renders the child Application plus definitions/config templates/schemas/views, applies auxiliaries, persists arguments in a Secret, and continues or restarts the child workflow.

**Add-on as a component.** A `type: addon` component invokes `vela/addon.#Render`. The feature-gated CueX provider calls the render-only service, which resolves latest or an exact version, validates system requirements, renders the child Application, folds auxiliaries into deterministic `k8s-objects` components, disables implicit apply-once, and returns the child Application as component output. The outer Application tracks the child; the child tracks and heals its auxiliaries. Admission validation resolves the same registry data and fails open on lookup failures, denying only a concrete version mismatch.

The registry refactor sits below both lifecycles, so their external contracts should not change.

## Findings

### Duplicated or misleading structure

- `versionedRegistry` and `ociRegistry` duplicate `GetAddonUIData`, `GetAddonInstallPackage`, `GetDetailedAddon`, archive decoding, package projection, registry stamping, and available-version attachment.
- `IsVersionRegistry` means “has a Helm block,” while `isVersionCapableRegistry` means the actual capability. This naming split caused OCI-specific repairs throughout cache, installer, helper, and CLI code.
- Callers alternate between `ToVersionedRegistry`, `BuildVersionedRegistry`, and `BuildOCIRegistry`, producing repeated transport switches.
- `Registry` permits both `Helm` and `OCI`, but precedence is inconsistent: read/list paths prefer Helm, push routes to OCI, and secret lifecycle follows OCI because Helm is not a `TokenSource`. This is accidental operation-specific behavior created by the representation, not a useful domain concept.
- `OCIAddonSource.Token` is used as a Basic-auth password, making the credential model harder to reason about.
- `findLegacyAddonDefs` checks only `IsVersionRegistry`; an OCI-installed legacy add-on takes the reader path and cannot build a reader. `getAddonVersionMeetSystemRequirement` is likewise HTTP-Helm-only.

### Genuinely OCI-specific behavior

- OCI has no Helm `index.yaml`, so cross-addon discovery needs the portable catalog and optional Distribution catalog fallback.
- OCI versions are repository tags and Helm 3.14.4's `Client.Tags` accepts strict semver tags, normalizes build metadata, and drops non-compliant tags such as `v0.0.1`.
- OCI pull/push and login require Helm's registry client, not the HTTP getter.
- ECR and other registries may not implement `/v2/_catalog`; `ErrOCICatalogAbsent` and the conservative catalog overwrite checks prevent silent catalog loss.
- OCI catalog publication has an unavoidable optimistic race because the Distribution API has no conditional put. The existing read/recheck/retry behavior must remain intact.

These differences belong behind a backend boundary, not in a second add-on registry façade.

### Target contracts and decisions

1. Add `IsOCIURL` using URL parsing and introduce a checked constructor, `NewVersionedRegistry(...) (VersionedRegistry, error)`, that chooses an HTTP or OCI backend from the scheme and rejects unsupported scheme/option combinations. Keep the exported `BuildVersionedRegistry` and `BuildOCIRegistry` signatures as deprecated adapters during the compatibility window; internal callers use the checked constructor.
2. Introduce an internal `resolvedChart` carrying archive bytes, selected version metadata, available versions, and whether transport metadata should override package metadata. This prevents the façade from knowing how the chart was fetched.
3. Put `GetAddonUIData`, `GetAddonInstallPackage`, `GetDetailedAddon`, archive loading, `loadAddonPackage`, and registry stamping on one `helmRegistry`.
4. Keep HTTP behavior in an `httpHelmBackend`: index loading, URL joining, basic/TLS options, and existing `chooseVersion` semantics.
5. Keep OCI behavior in an `ociHelmBackend`: repository refs, strict-semver tag listing, pulls, portable catalog preference, Distribution catalog fallback, and `ErrOCICatalogAbsent`.
6. Keep push as one command-level route selected by the canonical source URL. ChartMuseum upload and OCI push/catalog update remain separate backend operations.
7. Preserve current version and metadata semantics during this refactor. In particular, do not accidentally align prerelease selection, `v`-prefix handling, pinned `AvailableVersions`, or SystemRequirements overrides without dedicated tests and an explicit compatibility decision. Model these as explicit resolved fields rather than one generic “metadata override” boolean.
8. Route all chart-backed call sites through `ToVersionedRegistry`; the only remaining high-level branch is chart-backed versus `AsyncReader`-backed.
9. Keep compatible-version suggestions capability-aware. The HTTP backend may use index annotations as today; the OCI backend returns “no suggestion” until requirements are available without guessing (for example through a future enriched catalog or explicit candidate pulls).

## Backward-compatible configuration migration

- Keep `Registry.OCI`, `OCIAddonSource`, `IsOCIRegistry`, and `BuildOCIRegistry` as deprecated compatibility APIs until an explicit migration completion gate is met. `BuildOCIRegistry` becomes a thin wrapper over the unified URL-based factory; it no longer constructs a separate implementation.
- Continue decoding existing ConfigMap entries shaped as `{"oci":{"url":"oci://...","username":"...","tokenSecretRef":"..."}}`. Load the referenced Secret first, then adapt the source to the canonical Helm-source runtime shape.
- During the mixed-version/rollback window, the CLI accepts both `--type oci` and `--type helm --endpoint=oci://...` but continues writing the legacy `Registry.OCI` JSON shape for OCI URLs. This lets older binaries read the record correctly. Canonical Helm-shaped OCI writes begin only after the minimum supported version can read them, or through an explicit migration command that warns rollback is no longer supported.
- Derive displayed type from the URL, so `registry list/get` still says OCI for an `oci://` source.
- Preserve current behavior for pre-existing mixed-block records by operation: Helm for read/list/enable, OCI for push, and OCI for secret cleanup. Reject creation or migration of a mixed-block record, and require the migration command to ask which source wins rather than silently choosing.
- Add `passwordSecretRef` to the canonical Helm source. During the compatibility window, credential Secrets dual-read `password` then legacy `token`, and writes for OCI compatibility retain the `token` key older binaries expect. Do not migrate HTTP Helm passwords in this refactor.
- Make update cleanup old-record-aware. Before overwriting a registry, load its previous source and delete an obsolete credential Secret when credentials are removed, the source switches, or the secret reference changes. Deletion must remove either legacy OCI or canonical Helm credential Secrets.
- Do not rewrite every registry record merely because it was read. Provide an explicit `vela addon registry migrate` path (or equivalent one-shot controller job), emit deprecation warnings for legacy records, and remove the legacy fields only after migration telemetry/audit shows no OCI-shaped records within the supported upgrade range. A time-only deprecation window is insufficient.

## Ordered implementation plan

1. **Characterize contracts before moving code.** Add tests for URL classification, mixed Helm+OCI precedence, existing ConfigMap decoding, secret-backed legacy OCI auth, exact pins, empty-version resolution, prerelease behavior, SystemRequirements metadata, catalog absence, and error wrapping. Keep the current targeted suites green.
2. **Introduce checked source normalization.** Add URL classification, `NewVersionedRegistry(...) (VersionedRegistry, error)`, and a registry-to-chart-source adapter in `source.go` / `registry.go`. Extend the canonical credential shape without changing Git/OSS sources or mixed-version writes.
3. **Freeze error and metadata contracts.** Add the operation-by-operation error matrix and field-level metadata assertions before moving archive decoding. Refactor `versioned_registry.go` only after those tests pin both backends.
4. **Create the backend seam.** Refactor `versioned_registry.go` into the shared `helmRegistry` façade plus `chartBackend` and an explicit `resolvedChart` result.
5. **Move HTTP behavior unchanged.** Extract index/list/version/download logic from the current `versionedRegistry` into `httpHelmBackend`; retain `chooseVersion`, relative URL handling, HTTP options, and annotation override behavior.
6. **Move OCI behavior without weakening safety.** Replace `ociRegistry` with `ociHelmBackend`; keep registry-client construction, tag filtering, portable catalog discovery, pagination-host validation, absence classification, and pull errors. Adapt `oci_catalog.go` to the shared source/credential input.
7. **Collapse call-site switches selectively.** Update cache, installer, detailed package lookup, exact-version lookup, legacy definition lookup, CLI listing, and compatibility paths to use `ToVersionedRegistry`. Keep compatible-version suggestions backend-capability-aware so OCI never gets a false “compatible” recommendation.
8. **Unify push routing without changing legacy mixed records.** Resolve unambiguous configured registries to a canonical chart source and select ChartMuseum versus OCI from its URL. For an existing mixed-block record, preserve current OCI-first push behavior until explicit migration.
9. **Migrate CLI parsing and presentation.** Treat `--type oci` as a deprecated alias and permit `--type helm` with `oci://`, but keep legacy OCI-shaped writes during the rollback window. Show type from URL and validate OCI adds without rejecting a genuinely fresh catalog.
10. **Add explicit migration and cleanup.** Implement old-record-aware Secret cleanup, deprecation warnings, and a migration command/audit path. Gate canonical writes and eventual field removal on the supported-version policy and migration completion, not elapsed time.
11. **Delete duplicate implementation code.** Remove the `ociRegistry` struct and its duplicated VersionedRegistry methods. Retain OCI backend/catalog files and deprecated exported wrappers until the compatibility gate is met.
12. **Verify from unit boundary to lifecycle.** Run focused registry tests, package tests, render/provider/webhook tests, CLI tests, rollback fixtures, and an add-on component smoke against both an HTTP Helm fixture and an OCI fixture.

## Reuse and deletion

**Reuse unchanged or nearly unchanged:** `VersionedRegistry`; `MemoryReader`; `loadAddonPackage`; `chooseVersion`; Helm's cached index helper; OCI ref/tag/pull helpers; portable catalog encode/decode and safe publication loop; `Cache.cacheVersionedUIData`; installer/rendering logic; add-on component provider and CUE contract.

**Delete in the implementation PR:** the concrete `ociRegistry` type; its duplicated `GetAddonUIData`, `GetAddonInstallPackage`, and `GetDetailedAddon`; direct `BuildOCIRegistry` call sites; `isVersionCapableRegistry`; Helm-vs-OCI switches in helper/cache/CLI listing; tests whose only purpose is proving OCI takes a separate branch.

**Deprecate, then delete only after a migration gate:** exported `OCIAddonSource`, `Registry.OCI`, `IsOCIRegistry`, `BuildOCIRegistry`, and the `--type oci` spelling. Their first-stage implementations are adapters, not independent behavior. Removal requires the supported-version floor to understand canonical records and an audit showing no legacy or ambiguous mixed-block entries.

## Risks and edge cases

- **Credential regression:** canonicalizing OCI into Helm must not move a secret-backed password into the ConfigMap. Add a canonical password-secret reference before changing writes.
- **Version-policy drift:** HTTP and OCI differ today on prereleases, leading `v`, pinned version listings, and SystemRequirements metadata. Preserve behavior first; normalize only in a separately approved change.
- **Catalog safety:** never treat a generic 404, auth error, timeout, or empty strict-semver result as proof that the portable catalog is absent. Preserve the NAME_UNKNOWN-only overwrite gate and retry loop.
- **Fresh registry validation:** an OCI registry with no catalog is a valid empty source. CLI add must accept genuine `ErrOCICatalogAbsent` without masking auth/connectivity failures.
- **Both blocks populated:** keep Helm precedence until malformed records are no longer supported.
- **Transport options:** `InsecureSkipTLS`, custom CA/cert/key, and plain HTTP do not currently have identical HTTP/OCI meanings. Reject unsupported options rather than silently ignoring them.
- **Registry ordering:** retain deterministic name sorting because first matching registry wins.
- **Mutable credentials:** ECR passwords expire. Do not copy credentials into long-lived backend singletons beyond the lifetime already implied by the registry object/cache refresh.
- **Push semantics:** HTTP “Helm push” is specifically ChartMuseum upload; OCI uses Helm registry push. The façade must not pretend every HTTP Helm repository is writable.
- **Component lifecycle:** the add-on component returns a child Application and auxiliaries; changing registry internals must not change ownership, state-keep policy, resolved version, or registry labels.
