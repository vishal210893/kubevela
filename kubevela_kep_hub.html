The Orchestration Gap

Why do we need Cluster Infrastructure Orchestration?

A human-friendly explanation of the problem KubeVela is solving.

lightbulb The Core Problem

KubeVela is incredible at deploying applications (via the Application CRD). However, those applications assume the cluster they land on is already fully prepared. They assume networking (CNI, Ingress), security (OPA, Cert-Manager), and observability (Prometheus, Loki) are already perfectly configured.

But who sets up the cluster? Usually, platform teams stitch together a fragile mess of Terraform scripts, Helm charts, and manual kubectl commands. There is no standard, composable way to declare: "A production cluster requires this specific networking setup, this security setup, and this cloud VPC."

warning

Crucial Distinction: KubeVela does not provision machines or cloud resources directly. It delegates to tools like Cluster API (CAPI), Crossplane, or Terraform.

KubeVela's job is Orchestration: Composing these tools together, enforcing team ownership boundaries, and safely rolling changes across a fleet of clusters.

architecture The Hub-Spoke Architecture

To manage a fleet, we use a Hub-Spoke model. You manually create one "Hub" cluster using whatever tool you like. You install KubeVela on it. From that moment on, all declarative state for your infrastructure lives on the Hub. The Hub pushes actual infrastructure components out to the Spoke clusters.

The Core Abstractions

How we define infrastructure using Planes, Blueprints, and Clusters.

Think of building a cluster like building a house. A ClusterPlane is a specific system (plumbing, electrical). A ClusterBlueprint is the architectural diagram connecting those systems. The Cluster is the actual house.

layers 1. ClusterPlane

A composable infrastructure layer owned by a specific team. For example, the networking team owns the Networking Plane (Ingress, CNI). A plane is just a template; creating one does not spin up any infrastructure.

Deep Dive: ClusterPlane YAML & Versioning expand_more

Planes use semantic versioning. Adding the plane.oam.dev/publishVersion annotation takes an immutable snapshot, creating a ClusterPlaneRevision.

apiVersion: core.oam.dev/v1beta1
kind: ClusterPlane
metadata:
  name: networking
  annotations:
    plane.oam.dev/publishVersion: "2.3.1"
spec:
  components:
    - name: cilium
      type: helm-release
      properties:
        chart: cilium
        version: "1.14.4"
    - name: ingress-nginx
      type: helm-release
      dependsOn: [cilium] # Waits for CNI
      properties:
        chart: ingress-nginx

map 2. ClusterBlueprint

A complete cluster specification. It composes multiple ClusterPlanes together and defines their dependency order. Blueprints are immutable once published.

Deep Dive: Blueprint Resolution & SemVer expand_more

Blueprints support Semantic Versioning constraints (e.g., >= 2.0.0) for Planes. The controller automatically resolves this to the newest matching ClusterPlaneRevision.

apiVersion: core.oam.dev/v1beta1
kind: ClusterBlueprint
metadata:
  name: production-standard
spec:
  planes:
    - name: networking
      ref:
        name: networking
        version: ">= 2.0.0" # SemVer Constraint
    - name: security
      ref:
        name: security
        version: "1.8.0"

dns 3. Cluster

The first-class representation of the actual managed cluster. It points to a Blueprint, manages connectivity credentials, and holds the actual, aggregated status of everything running inside it.

Controller Ownership & GitOps

How reconciliation works without infinite loops.

sync Pull-Based Reconciliation

A massive architectural decision in KubeVela: Planes and Blueprints are templates. Creating them does nothing.

Infrastructure is only created when a Cluster references a Blueprint. This is a pull model. The ClusterController reads the blueprint, resolves the planes, and pushes the resources to the actual cluster.

block Circular Reference Prevention

In Kubernetes, if Controller A modifies Controller B's spec, and Controller B modifies Controller A's spec based on status, you get an infinite loop that crashes the API server. KubeVela prevents this via strict ownership.

info

The Golden Rule: Controllers NEVER modify `spec` fields they don't own. Cluster.spec.blueprintRef is owned strictly by the User or a GitOps tool (like ArgoCD). The Controllers only ever write to status fields.

Cluster Lifecycle & Fleet Rollouts

Managing clusters from birth to death, safely across a fleet.

published_with_changes Lifecycle Modes

A cluster can exist in three modes:

  1. Provision: KubeVela uses a tool (like Crossplane) to provision the actual cloud VPC and Kubernetes API from scratch.
  2. Adopt: You hand KubeVela a kubeconfig to an existing cluster, and it takes over managing the infrastructure inside it.
  3. Connect: KubeVela just connects to the cluster to deploy app workloads, but does not manage the base infrastructure.

tsunami Wave-Based Fleet Rollouts

When you update a Blueprint (say, upgrading your CNI version), you don't want all 50 of your production clusters to update instantly. What if it breaks? KubeVela uses a ClusterRolloutStrategy to gate updates.

event Maintenance Windows

Even if a rollout wave is active, a specific cluster might have a strict maintenance window (e.g., "Only update Saturday 2 AM - 6 AM"). The ClusterController computes this dynamically and will generate a ClusterRolloutCheckpoint, pausing the update for that specific cluster until the window opens.

Drift Detection & Observability

Keeping reality in sync with your declarative state.

policy Drift Detection

What happens if a developer manually edits a Deployment inside a production Spoke cluster using kubectl? The cluster has "drifted" from the Blueprint.

The ClusterController continuously polls the Spoke clusters. If it detects drift, it updates the Cluster's status.drift field and generates a ClusterDriftReport.

Deep Dive: Drift Exceptions expand_more

Sometimes drift is expected (e.g., an HPA scaling replicas up and down). You can define a ClusterDriftException to tell KubeVela to ignore changes to specific fields.

apiVersion: core.oam.dev/v1beta1
kind: ClusterDriftException
metadata:
  name: ignore-hpa-replicas
spec:
  target:
    kind: Deployment
    name: ingress-nginx-controller
  ignoreFields:
    - "spec.replicas"

monitor_heart Health Aggregation

How do you know if a Cluster is healthy? KubeVela aggregates health from the bottom up:

  • Component Health: Probes standard Kubernetes objects (Pods Ready, Services running).
  • Plane Health: Aggregates the health of all components inside that plane.
  • Cluster Health: Aggregates the health of all Planes. If one plane is degraded, the whole cluster is marked Degraded.
