1 Big picture

Reconciler

Singleton controller. Wires the full pipeline inside one Reconcile() function. application_controller.go:109

AppHandler

Created fresh each reconcile. Tracks applied resources, service health, and holds the ResourceKeeper handle.

appfile.Parser

Converts the Application CR to an in-memory Appfile by loading all referenced definitions from the cluster or a pinned revision.

Appfile

Central data bag for one reconcile. Holds parsed components, traits, workflow steps, policies, and the CUE templates for each.

WorkflowExecutor

Runs compiled TaskRunners in DAG order, calling back into applyComponentFunc / checkComponentHealth closures for each component.

ResourceKeeper

Owns resource dispatch (server-side apply), drift prevention (StateKeep), and garbage collection. Backed by ResourceTracker CRs.

The controller does not diff spec vs cluster before acting. Every reconcile re-parses, re-renders, and re-dispatches. The dispatcher skips the API call only if the component is already healthy and properties are unchanged (dispatcher.go:167).

2 Entry point

Everything starts at func (r *Reconciler) Reconcile(ctx, req) in application_controller.go:109. The function is annotated // nolint:gocyclo by design — the entire pipeline runs top-to-bottom in one place so the control flow is easy to follow.

Watch sources application_controller.go:662

SetupWithManager registers three sources:

  • For(&Application{}) — every Application create/update/delete
  • Watches(ResourceTracker) — delete events only; re-queues the app when a tracker is GC'd externally
  • Watches(PolicyDefinition) — invalidates the policy cache when a definition changes

Update filter application_controller.go:673

The UpdateFunc predicate strips workflow status fields, AppliedResources, Services, and ResourceVersion before DeepEqual. Without this, every status write by the workflow executor would trigger a new reconcile.

3 Pipeline — step by step

1
Fetch and pre-check application_controller.go:116
The controller needs to know two things before doing anything: does this app still exist, and is it allowed to act on it? If the app was deleted between the watch event and now, bail out silently. If it was paused, or is owned by a different controller version, stop here. A copy of the current status is saved at this point so the final status write can diff against it and skip the API call if nothing actually changed.
2
Create AppHandler + handle finalizers apply.go:78 · application_controller.go:153
The AppHandler is the controller's working memory for this reconcile — it knows what the app currently owns and where. It reconstructs this picture by loading all ResourceTracker CRs from the cluster on every run. The finalizer is what makes safe deletion possible: when someone deletes an Application, the controller intercepts it, garbage-collects all owned resources and revisions, and only then removes the finalizer so the object can disappear.
3
Apply Application-scoped policy transforms application_controller.go:165
Some policies don't deploy resources — they modify the application spec itself. An override policy might replace component parameters across environments; an application-scope policy might inject annotations or swap component types. These run before parsing so everything downstream sees the transformed spec as if that's what the user originally wrote.
4
Generate Appfile application_controller.go:180 → parser.go:87
The application spec is just names and parameters. To actually deploy anything, the controller needs the full CUE templates behind those names — what schema a component accepts, what a trait renders, what a health check evaluates. This step resolves all of that into one in-memory struct. If a publish-version annotation is set, it reads from a frozen revision instead of the live cluster, which is how pinned deployments and rollbacks work.
5
Prepare ApplicationRevision application_controller.go:188
Before deploying anything, the controller captures a snapshot of the entire spec plus all referenced definitions in an ApplicationRevision. This is the rollback artifact. If someone later patches a TraitDefinition in the cluster, existing apps keep running against their frozen version. Rollback means pointing the app at an older revision, not hoping the cluster's current definitions match what was running before.
6
Apply policies application_controller.go:211 → apply.go:469
Non-application-scope policies (replication, isolation, topology) generate actual Kubernetes resources. This step renders those resources through their CUE templates and applies them to the cluster before workflow execution starts, so the infrastructure policies depend on — namespaces, placement, network rules — is already in place when components begin deploying.
7
Generate workflow steps application_controller.go:222 → generator.go:70
The workflow is compiled into a program here, not interpreted at runtime. Each step's CUE gets compiled into a TaskRunner. The controller also decides whether to restart the workflow from scratch (new revision, restart annotation, changed helm values fingerprint) or resume from where it left off. Without resumption, a long-running workflow with a deploy step that takes minutes would restart from step one on every reconcile.
8
Execute workflow application_controller.go:236
The executor runs each TaskRunner in DAG order and returns a single state that determines everything the controller does next. Executing Suspending Terminated Failed Succeeded Skipped Only Succeeded reaches health evaluation and full GC. Every other state takes a different exit path. If your app seems stuck, this state is the first thing to check.
9
Per-component apply generator.go:306 → generator.go:378
Each component goes through its own mini-pipeline: load its definition, run the CUE template to produce Kubernetes objects, stamp ownership labels, then apply. When MultiStageComponentApply is on, traits are dispatched in waves — PreDispatch traits run before the workload exists, DefaultDispatch traits run with it, and PostDispatch traits run only after the workload is confirmed healthy. This ordering is what allows a sidecar injector trait to run before the workload, or an external-dns trait to wait until an IP is assigned.
10
Workflow state routing application_controller.go:280
The workflow state is the most important branch in the reconcile. Succeeded is the only path to full health evaluation, PostDispatch traits, and complete GC. Terminal states (Terminated, Failed) record end-time and metrics then requeue at the default resync period. Suspending holds without re-running completed steps. If an app's PostDispatch traits are never applying, or GC seems partial, start here — the workflow state explains why.
11
Health evaluation application_controller.go:326 → apply.go:325
Applying a resource doesn't mean it's healthy. This step evaluates each component's health expression — defined in CUE inside the ComponentDefinition — against the live cluster object. It's not polling Pod ready conditions; it's running a programmable check that each definition author writes. A Deployment might be considered healthy only when all replicas are ready and a specific annotation is present. The result here sets the app phase to Running or Unhealthy.
12
PostDispatch traits apply.go:524
PostDispatch traits exist for one reason: they need runtime information the workload didn't have when it was first applied. A load balancer IP isn't known until the Service exists. An external-dns trait that registers a DNS record can't run until that IP is assigned. For each healthy component, the live workload is fetched and injected into the trait's CUE context as context.output, giving the trait access to anything the workload wrote to its status.
13
StateKeep and GarbageCollect application_controller.go:336
KubeVela doesn't trust that the cluster matches desired state between reconciles. StateKeep re-applies every owned resource on each successful reconcile — that's what "self-healing" actually means in practice. Someone manually edits a Deployment's replica count, and the next periodic reconcile corrects it. GarbageCollect is the inverse: resources that used to belong to this app (a removed component, a deleted trait) are cleaned up here, as are old ApplicationRevisions past the retention limit.
14
Write status application_controller.go:362
The final status write persists everything collected during the reconcile: which services are healthy, which resources are owned, what the workflow state is. The diff against the snapshot from step 1 is what prevents this from triggering another reconcile — the update predicate in SetupWithManager strips status fields, but a no-op write is still wasted API traffic. If the status hasn't changed, the call is skipped entirely.

7 Error handling and requeue

Central error path

All non-fatal reconcile errors go through r.endWithNegativeCondition(ctx, app, condition, phase) application_controller.go:530. It sets the condition on app.Status, patches to the API server, then returns the error. controller-runtime requeues immediately with exponential backoff. The condition shows up in kubectl describe application.

Requeue builder application_controller.go:430

Every return path uses the *reconcileResult fluent builder:

  • r.result(err).ret() — immediate requeue on error, otherwise ApplicationReSyncPeriod
  • r.result(err).requeue(d).ret() — explicit requeue after duration (workflow backoff)
  • r.result(err).forApp(app).ret() — honours app.oam.dev/reconcile-interval annotation (minimum 10s)

10 Senior engineer digest

Key facts

1
Everything — CUE templates, definitions, workflow steps, policies — resolves into the in-memory Appfile before any dispatch happens. Start at parser.go:87 GenerateAppFile to understand what gets applied.
2
The ApplicationRevision CR is a frozen snapshot of all definition CUE at revision-creation time. Rollback works by reading from the revision, not live cluster definitions.
3
The workflow executor never calls apply/render directly. It receives them as RuntimeParams.ComponentApply etc. — closures created in GenerateApplicationSteps that capture AppHandler, appParser, and af.
4
ResourceKeeper uses server-side apply, so every dispatch is idempotent at the API level. The dispatcher adds an optimization layer that skips the call entirely when the component is healthy and properties are unchanged. dispatcher.go:167
5
PostDispatch traits are a deliberate second pass. They are filtered out during the initial apply while the component is unhealthy. When they eventually run, the live workload object is fetched and injected as context.output so traits can read runtime-populated fields.
6
Health is CUE evaluation, not Kubernetes condition polling. The health expression in the definition's template is run against the live cluster object. If it returns isHealth: false, the component is unhealthy regardless of Pod ready conditions.
7
KubeVela does not use .Owns(). ResourceTracker CRs record every resource the app owns. ResourceTracker delete events re-queue the application. controller:816
8
The UpdateFunc predicate strips workflow status, services, and applied resources before DeepEqual. This is why frequent workflow executor status writes don't trigger new reconciles.
9
writeStatusByMethod compares app.Status against the copy stored at reconcile start. If nothing changed, the status patch is skipped.
10
isHealth=false is not an error. A component that dispatched successfully but isn't healthy yet returns (false, nil). The workflow step retries on its own schedule. Only an API error or CUE failure causes an error requeue.
11
ParseComponentFromRevisionAndClient tries the frozen revision first; falls back to the live cluster if a definition is absent from the revision. The fallback only triggers when absent, not when different — hot-patching a definition without bumping publish-version won't take effect.
12
componentPropertiesChanged compares against the current revision by default. When autoRevision=true it compares against the previous revision, which detects policy-driven mutations.

Common pitfalls

Infinite reconcile from status fields If you add fields to app.Status that are updated during workflow execution, add them to the UpdateFunc predicate in SetupWithManager. Missing this causes a reconcile storm: the status write triggers a new reconcile which writes status again.
PostDispatch context.output is nil until component is healthy If your PostDispatch trait CUE references context.output.status.loadBalancer, it will get a zero value on the first reconcile while the component is still being created. Always guard with if context.output != _|_ && ....
Hot-patched TraitDefinition not picked up The fallback in ParseComponentFromRevisionAndClient only kicks in when a definition is absent from the revision, not when it has changed. Updating a TraitDefinition without bumping publish-version leaves existing apps on the frozen version.
GarbageCollect finished=false is not an error When a resource has a finalizer and is waiting to be deleted, GC returns finished=false, waiting=[...]. The reconciler requeues with baseGCBackoffWaitTime=3s. Logging this as an error causes alert fatigue.
componentPropertiesChanged JSON comparison is byte-level Properties are compared as raw JSON bytes. Key ordering differences between a fresh json.Marshal and bytes stored in the revision can produce false-positive re-dispatches if external tools update the Application spec in a different field order.
