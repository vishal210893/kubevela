Orientation, in one paragraph

KubeVela today can deploy workloads to a cluster that somebody else already built. This epic is about the opposite direction: you write one Kubernetes object, apply it to a hub cluster, and an EKS cluster appears in AWS, wired up and registered, with no Terraform run and no runbook. The specification for that already exists as a KEP. None of it has been implemented. The epic's job is to implement the first slice of it and prove the slice against a real AWS account.

Where this sits relative to what already shipped

Two earlier pieces of work matter here. Revelstoke shipped the SpokeCluster kind with a mode field that accepts only connect, so KubeVela can take over a cluster that exists. GWCP-108609 extended that to Atmos. This epic opens the provision value of that same field, which is the mode that creates a cluster rather than adopting one.

Paragraph 1: what is being built and in what order

Land the Provision slice (KEP Mode 1: Provision, Create New Cluster) of the Cluster Infrastructure Abstraction KEP in KubeVela OSS, and prove it by standing up a bare-minimum Atmos EKS cluster from a SpokeCluster CR. Provision is the mode that creates a cluster, and it is the seam Revelstoke deliberately left closed: GWCP-102121's webhook and GWCP-105243's CEL rules reject mode: provision today. This epic opens it.

The order of work follows the KEP's lifecycle phases. infraProvisioning runs on the hub, against cloud APIs, before the spoke exists, it provisions the prerequisites (VPC, subnets, NAT/IGW, IAM roles and OIDC, Route53 zone where needed) and then the EKS cluster itself, publishing outputs (vpcId, privateSubnets, clusterEndpoint, oidcProviderArn) that downstream planes consume. Only once the cluster exists do the spoke-reconciled phases run: clusterInit (foundational layer), planeProvisioning (the dispatched blueprint's planes), and healthValidation. Prereq infrastructure is modelled as a scope: shared ClusterPlane so a second cluster in the same region consumes the existing VPC/IAM outputs instead of re-creating them; the per-cluster EKS plane is scope: perCluster and imports those outputs via inputs.fromPlane.

"The seam Revelstoke deliberately left closed"

A seam is a place in the code that was shaped for a future change but left switched off. The mode field is one. The API already has three legal-looking values in the design, but validation only lets connect through. Two mechanisms do that rejection, and both have to be relaxed by this epic:

MechanismWhere it runsWhat it does todayTicket
Validating admission webhookA pod in the hub cluster, called by the API server before the object is storedRejects any mode other than connect, with a messageGWCP-102121
CEL validation rules on the CRDInside the API server itself, compiled from the CRD schemaSame restriction, enforced without a webhook being reachableGWCP-105243

Both exist because a partially implemented mode is worse than an absent one. A user who applies mode: provision against today's controller would get an object that is accepted and then silently does nothing. Rejecting it at admission means the API never lies about what it can do.

The lifecycle phases, and why the order is the plan

The KEP splits the life of a managed cluster into four phases. The important property is not the names, it is where each phase is reconciled, because that determines what has to exist before it can run.

PhaseRuns onActs onExamples from the KEP
infraProvisioningHubCloud provider APIsVPC, IAM roles, DNS zones
clusterInitSpokeThe spoke clusterCNI, base controllers and operators, Helm runtime, base CRDs
planeProvisioningSpokeThe spoke clusterCilium, cert-manager, ingress, monitoring agents
healthValidationSpoke, read by the hub on demandThe spoke clusterValidation apps, smoke tests, readiness checks

KEP anchor: lines 3906-3919 (execution model table), 4237-4320 (phase definitions and the deletion order).

Only the first phase can run before the cluster exists, which is exactly why provision mode is harder than connect mode. In connect mode all four phases have a live API server to talk to from the first reconcile. In provision mode the hub has to talk to AWS, not to Kubernetes, for the entire first phase, because there is no spoke API server to talk to yet. The KEP states this directly: "Runs on the hub; no spoke exists yet."

The ordering claim in the epic is therefore a claim about dependencies, not about taste. You cannot install a CNI into a cluster that has not been created. You cannot create an EKS cluster without subnet IDs. So the work has to be built in the order the dependencies run, and the epic's thin slices follow that order: slice 1 stops at prerequisites, slice 2 adds the cluster itself.

Outputs, and why they are the load-bearing idea

An output is a value one piece of infrastructure publishes after it is created, which another piece then reads as an input. The four named in the epic are the handoff points between the shared prerequisite layer and the cluster layer:

OutputProduced byConsumed by
vpcIdThe VPC component in the shared planeThe EKS cluster component
privateSubnetsThe subnet components in the shared planeEKS control plane and node group placement
oidcProviderArnThe IAM component in the shared planeIRSA on the new cluster
clusterEndpointThe EKS componentThe gateway registration that hands off to connect mode

In the KEP the plumbing for this is explicit. A plane declares what it publishes under outputs[].valueFrom, naming a component and a field path inside that component's own status. A consuming plane declares inputs[] with fromPlane and output, naming the plane and the output it wants.

# Shared plane publishes
outputs:
  - name: vpcId
    valueFrom:
      component: vpc
      fieldPath: outputs.vpc_id

# Per-cluster plane consumes
inputs:
  - name: vpcId
    fromPlane: shared-vpc-us-east-1
    output: vpcId

KEP anchor: lines 6516-6600, Use Case 5, multi-cluster shared VPC.

scope: shared against scope: perCluster

Every ClusterPlane carries a scope. It answers one question: when two clusters both reference this plane, do they get one copy of the infrastructure or two?

  • scope: shared means one copy. The first cluster to reference it causes the infrastructure to be created. The second consumes the outputs of what already exists. A VPC, its NAT gateways and the IAM baseline belong here, because three clusters in one region sharing one VPC is the normal production layout and re-creating it per cluster wastes address space and money.
  • scope: perCluster means one copy each. The EKS control plane and its node group belong here, because "share the cluster between clusters" is meaningless.

The KEP also restricts who may consume a shared plane, through sharedWith.clusterSelector, which is an ordinary label selector matched against the SpokeCluster. A production VPC can be declared shareable only with clusters labelled for that region and environment.

A detail worth internalising early: a ClusterPlane does nothing on its own

The KEP is emphatic that a ClusterPlane is a template, not a self-reconciling object. Creating one validates the schema and may cut a revision. It creates no cloud resources. Infrastructure appears only when a SpokeCluster references a blueprint that contains the plane. The KEP calls this the pull model, and the reason given is that it leaves no orphaned infrastructure, since every real resource traces back to a SpokeCluster that asked for it.

KEP anchor: lines 1045-1080.

Paragraph 2: why Crossplane, and what already exists

The provisioning backend is Crossplane, wired through ClusterProviderDefinition.spec.schematic.crossplane.compositionRef. The KEP is explicitly backend-agnostic (Crossplane, CAPI, tf-controller, ACK, KRO), and Crossplane is the right choice for Atmos because the substrate is already there: atmos-crossplane-providers ships and enables provider-aws-ec2, provider-aws-iam, provider-aws-eks and provider-aws-route53 today, all IRSA-bound via aws.iamRoleArn, and CCS-atmos-oam-library already carries 12 Crossplane compositions with vcluster as a cluster-shaped precedent (XRD + claim + Ginkgo suite). The new work is the XRDs and Compositions for the shared VPC/IAM prereq plane and the bare-minimum EKS plane, not a new provider family.

What backend-agnostic actually means here

The KEP is careful about KubeVela's role. It says, in the positioning box near the top, that KubeVela does not provision clusters directly, and that provisioning is delegated to CAPI, Crossplane, Terraform, KRO or cloud-native operators. KubeVela's contribution is composition, ordering, rollout and ownership across those tools.

KEP anchor: lines 120-135, The Approach, and the delegation table at 95-119.

ClusterProviderDefinition is where that pluggability is expressed. It is a CRD whose schematic field has one arm per backend, and the KEP shows Crossplane, Terraform and a native controller as alternatives in the same object:

spec:
  provider: aws
  schematic:
    crossplane:
      compositionRef:
        name: eks-cluster-composition
    # terraform:
    #   moduleSource: "terraform-aws-modules/eks/aws"
    # native:
    #   controllerImage: "kubevela/cluster-provider-aws:v1.0.0"

KEP anchor: lines 4353-4440, including the aws-eks, gcp-gke, azure-aks and kind examples.

The epic keeps all the arms in the schema and implements only the Crossplane one. That is a deliberate trade: the extension point stays visible to the upstream community and to future GKE or CAPI work, while the delivery risk stays bounded to a single backend.

The rest of that CRD, which the epic also names

Three more fields on ClusterProviderDefinition appear in the epic's What section and are worth defining now, because they carry weight in the acceptance criteria:

FieldWhat it holdsWhy the epic cares
defaultsProvider-level defaults such as Kubernetes version, instance type, node counts, VPC CIDRLets a SpokeCluster stay short, since a user supplies credentials, region and a blueprint and nothing else
capabilitiesA list of things the provider supports, for example private endpoint, managed node groups, spot instancesDeclares what the backend can do without the controller hard-coding AWS knowledge
statusMappingsTranslation from backend-specific states into the standard phase machineEKS says CREATING, ACTIVE, FAILED. KubeVela has to say Provisioning, Ready, Failed. This field is the dictionary

The Atmos substrate argument

The second half of the paragraph is a cost argument rather than a design one. Four AWS Crossplane providers are already installed and enabled in Atmos, bound to AWS through IRSA. They currently back data-service compositions such as S3, EFS, Aurora and OpenSearch. Nothing has yet pointed them at the infrastructure that a cluster is made of. The claim is that the missing pieces are two compositions, not a new platform.

The vcluster precedent is doing specific work in this argument. It is an existing composition in the same library that produces something cluster-shaped, and it comes with the structure the new work is expected to copy: an XRD, a claim, and a Ginkgo suite that exercises it.

Crossplane vocabulary, since the paragraph leans on it

Paragraph 3: what "bare minimum" means

"Bare minimum" is a deliberate constraint: private API endpoint, IRSA enabled, one small system managed node group, and the access wiring the hub needs to reach it. No Atmos NG add-on stack, no Flux bootstrap, no full component set. The cluster must come up Ready, be reachable, and hand off cleanly to the Connect-mode gateway registration built in Revelstoke (GWCP-100435) and extended to Atmos in GWCP-108609, provision ends where connect begins, reusing the same cluster-gateway Secret contract rather than inventing a second one.

This paragraph is the scope fence. Each item in the list is there because leaving it out would make the demo dishonest, and everything not in the list is excluded because it would grow the work without proving anything new.

IncludedWhy it cannot be dropped
Private API endpointA public endpoint would be a different network design from the one Atmos runs, so a public-endpoint demo would not prove hub-to-spoke reachability
IRSA enabledRequires the OIDC provider from the prerequisite plane, so it proves the output wiring end to end
One small system managed node groupA cluster with no nodes is not reachable in a useful sense, and node groups are the component that has to wait for ACTIVE, which is the ordering guarantee being tested
Access wiring for the hubEither an EKS access entry or an aws-auth mapping. Without it the hub has an endpoint it is not authorised to use

"Provision ends where connect begins"

This is the most important sentence in the paragraph. Connect mode already knows how to register a cluster: it writes a Secret in a particular shape, with particular labels, which cluster-gateway reads in order to proxy requests. Everything downstream depends on that Secret and nothing else: vela cluster list, topology policies on an Application, read-through to spoke resources.

So provision mode is not asked to invent registration. It is asked to produce the same Secret, with the difference that the values inside it are derived from plane outputs (endpoint, CA, region) rather than pasted in by a human as a kubeconfig. The acceptance criterion attached to this is that an Application with a topology policy targeting the new cluster by name deploys through the existing gateway with no modification.

The KEP supports this framing in its backward-compatibility appendix, which discusses referencing existing cluster-gateway Secrets rather than replacing the mechanism.

KEP anchor: lines 7911-7945, Appendix A.

Paragraph 4: the hub is not in scope

The hub is not in scope to provision. Per the KEP's own prerequisite, KubeVela does not bootstrap the hub, an existing Atmos PD cluster running vela-cluster-core plus Crossplane serves as the management cluster. Rollout engine, drift detection, health providers, decommissioning workflow, maintenance windows and plane/blueprint revision publishing all remain in the parent KEP.

The first half is not a scoping preference, it is a constraint inherited from the KEP. The prerequisites table states that the hub cluster is bootstrapped by the platform team using Terraform, eksctl, the cloud console, CAPI or anything else, and the note underneath is unambiguous: "KubeVela does NOT bootstrap the hub cluster."

KEP anchor: lines 182-194.

There is no chicken-and-egg problem to solve, in other words. Something has to run the controller that creates clusters, and that something is created the old way, once.

The second half lists the parts of the KEP that stay on the shelf. The KEP is large, roughly eight thousand lines, and it specifies a full fleet-management product. This epic implements the creation path only. What is deferred:

Deferred capabilityWhat it would have added
Rollout engine (ClusterRollout, ClusterRolloutStrategy)Progressive, wave-based infrastructure changes across a fleet with checkpoints
Drift detection (ClusterDriftReport, ClusterDriftException)Noticing and remediating when a cluster stops matching its blueprint
Observability providers and the health hierarchyAggregated health from components up to fleet level
Decommissioning workflowStaged teardown with rollback checkpoints, as distinct from the plain reverse-order cleanup this epic does implement
Maintenance windowsEnforcing when changes are allowed to run
Revision publishing (publishVersion, draft mode, diff and rollback)Versioned, diffable, rollback-able planes and blueprints

Conflicts, gaps and assumptions

1. The KEP names the provision blueprint field in two different places

The Mode 1 section shows a top-level spec.blueprintRef and spec.provider on the SpokeCluster (KEP lines 3931-3960). The lifecycle phases section shows spec.infraProvisioning.blueprintRef alongside a separate top-level spec.blueprintRef, and uses spec.credential rather than spec.provider (KEP lines 4243-4270). The epic follows the second shape for infraProvisioning and the first for provider. Someone has to decide which is authoritative before the API types are written, because both shapes cannot ship.

2. The epic puts EKS creation inside infraProvisioning, which the KEP's own table does not say

The epic's first paragraph says infraProvisioning provisions the prerequisites "and then the EKS cluster itself". The KEP's execution model table lists only shared cloud infrastructure, that is VPC, IAM and DNS, under infraProvisioning. The KEP's phase notes do support the epic's reading indirectly, since they say that for mode provision "the cluster was already created during infraProvisioning on the hub", but the summary table and the phase description are not consistent with each other. This matters for where the per-cluster EKS plane is reconciled.

3. Shared-plane semantics are described at two levels and the epic mixes them

The KEP describes sharing both at plane level (scope: shared on a ClusterPlane, with status.consumers) and at blueprint level (two SpokeClusters referencing the same infraProvisioning.blueprintRef). The epic's acceptance criteria assert consumer tracking on the plane, while its scenario 6 asserts that referencing the same blueprint causes no re-reconciliation. Both are in the KEP, and the KEP says the blueprint-level behaviour is implemented by the plane-level mechanism. Worth confirming that the implementation keeps one source of truth rather than two counters.

Questions to settle before implementation starts

  1. Which field shape wins for provision mode, spec.provider plus a top-level blueprintRef, or spec.credential plus infraProvisioning.blueprintRef? Upstream review will ask.
  2. Is the per-cluster EKS plane part of the infraProvisioning blueprint, or a separate blueprint reconciled on the hub? The epic implies the former.
  3. Does the new feature gate cover the provision mode only, or the three new CRDs as well? A provision-gated mode with ungated ClusterPlane CRDs would let someone create planes that nothing can consume.
  4. Where does the hub get its authorisation to the new cluster, an EKS access entry created by the composition or an aws-auth mapping applied afterwards? The second needs API access that the first is supposed to grant, so the ordering has to be explicit.
