# KEP-2.13 Addon Controller — E2E Test Design

**Date:** 2026-06-15
**Branch:** `feat/kep-2.13-addon-types`
**Scope:** End-to-end (Ginkgo) tests for the *implemented* Addon-CR lifecycle
(GWCP-101811 CEL admission + GWCP-102617 reconcile → install → status → deletion).
**Stories:** GWCP-101811, GWCP-102617.

## 1. Goal

Add a Ginkgo e2e suite that exercises the reachable behaviour of the `Addon`
CRD controller against a real cluster, using the deterministic local mock
addon registry (`e2e/addon/mock`). Coverage is the **core lifecycle** agreed
with the author: CEL admission, happy install, the two failure branches, pause,
and the Protect deletion path (clean + blocked/unblock). Upgrade and the 10-min
escalation are explicitly out of scope (see §6).

This design is grounded in a full manual edge-case pass already run on a live
k3d cluster with the real `cmd/core`; the observed behaviour (including two
findings, F1/F2 below) is what the e2e asserts.

## 2. Environment & harness

- **Suite location:** new file `test/e2e-test/addon_crd_test.go`, joining the
  existing `OAM Core Resource Controller Suite` (`suite_test.go`,
  `config.GetConfigOrDie()` against a real cluster). Follows the existing
  `Describe`/`Context`/`It`/`By` conventions used by `application_test.go`.
- **Controller:** the `AddonCRD` feature gate must be **on** for the deployed
  vela-core. The gate default is currently `true` (local diff in
  `pkg/features/controller_features.go`); the e2e relies on that. If the gate
  is ever returned to `false`, the e2e setup must pass `--feature-gates=AddonCRD=true`.
- **Registry:** the **local mock** server (`go run ./e2e/addon/mock`, port
  9098) registered via `e2e/addon/mock/utils.ApplyMockServerConfig()`, which
  writes the `vela-addon-registry` ConfigMap with an OSS registry named
  **`KubeVela`** → `http://127.0.0.1:9098`. The mock is already started by
  `make e2e-setup-core-post-hook`. The suite ensures the CM exists in a
  `BeforeEach`/`BeforeAll` (idempotent).
- **Test addon:** `example` (v1.0.0) from mock testdata — dependency-free,
  applies a namespace + ConfigMap, and provides a `helm` ComponentDefinition
  used as the dependent for the blocked-deletion case. All CRs set
  `skipVersionCheck: true` so out-of-cluster / version-check-free runs work.
- **Isolation:** every `It` uses a **unique addon name** (e.g. suffixed) and an
  `AfterEach` that deletes the CR and waits for finalizer release, to avoid the
  orphaned-ResourceTracker churn observed in the manual pass (finding F3).

## 3. Test matrix

### 3.1 CEL admission (no controller needed — API-server validation)
Use `dryRunCreate` (server-side dry-run) so nothing persists.

| Case | spec | Expect |
|---|---|---|
| version constraint | `version: ">=1.2.0"` (and `1.x`, `latest`) | rejected, msg `semver constraints are not supported` |
| version exact | `version: "v1.2.0"`, `"1.0.0"`, `"v1.2.0-rc.1"` | accepted |
| deletionPolicy Force | `deletionPolicy: Force` | rejected, msg `only Protect is accepted` |
| deletionPolicy Orphan | `deletionPolicy: Orphan` | rejected |
| deletionPolicy Protect/empty | `Protect` / unset | accepted |

### 3.2 Reconcile / install / status
| Case | Setup | Expect (Eventually) |
|---|---|---|
| Happy | `example` v1.0.0, registry `KubeVela` | phase `running`; `Ready=True/Installed`; `SourceResolved=True/SourceFetched`; `installedVersion=1.0.0`; finalizer `addon.oam.dev/cleanup` present; owned Application `addon-example` exists |
| Registry unreachable | registry `NoSuchRegistry` | phase stays `installing`; `SourceResolved=False/RegistryUnreachable`, msg names the registry; phase is **not** `running` |
| Install failed | a broken-template addon (see §5) | phase `failed`; `SourceResolved=True/SourceFetched`; `Ready=False/InstallFailed` |
| Pause | happy addon, then add label `controller.core.oam.dev/pause=true` before/at create | controller logs `reconciliation paused`; status makes no further progress (assert phase unchanged over a short consistent window) |

### 3.3 Deletion — Protect only (the only CEL-reachable policy)
| Case | Setup | Expect |
|---|---|---|
| Clean | install `example`, no dependents, delete CR | owned Application `addon-example` removed **and** CR removed (finalizer released); app gone no later than CR |
| Blocked | install `example`, create an Application using `type: helm`, delete CR | phase `deleting`; `Ready=False/DeletionBlocked` listing the dependent; finalizer + owned app retained; CR persists |
| Unblock | from blocked, delete the dependent, then **nudge** the CR (annotate) | CR + owned app removed |

## 4. Key assertions / helpers

- `getAddon(name) *v1beta1.Addon` and small matchers for phase / condition
  `(type→status/reason)` to keep `It`s readable.
- `Eventually(... , 120*time.Second, 3*time.Second)` for install/running;
  `Consistently(...)` for the pause "no progress" assertion.
- Blocked→unblock uses an explicit annotate-nudge rather than waiting on the
  5-minute resync (finding **F1**: no Application watch re-triggers the addon).

## 5. Test data additions

- **Broken-template addon** for the InstallFailed branch: a minimal addon under
  `e2e/addon/mock/testdata/<name>/` whose `template.yaml`/resources fetch
  successfully but fail to render/apply (e.g. invalid CUE), producing a
  non-fetch error so the controller takes the `SourceResolved=True` +
  `failed/InstallFailed` branch deterministically. (A bad *version* is an
  `ErrFetch` and would instead hit the RegistryUnreachable branch, so it cannot
  serve this case.) The implementer picks the smallest reliable trigger and, if
  an existing mock addon already fails this way, reuses it instead of adding one.

## 6. Out of scope (with rationale)

- **Upgrade / `upgrading` phase** — finding **F2**: status is patched once at
  the end of reconcile, so on a clean upgrade the phase is already `running`
  before it is persisted; `upgrading` is not externally observable. Asserting it
  would be flaky. (A possible follow-up: assert only that `installedVersion`
  changes — deferred per the agreed "core lifecycle" scope.)
- **10-minute `SourceResolved`→`failed` escalation** — too slow for CI.
- **Force / Orphan deletion flows** — unreachable through the CRD (CEL rejects
  them); covered only as negative admission cases in §3.1.

## 7. Findings surfaced by manual testing (for the team, not test code)

- **F1** — A Protect-blocked deletion only re-checks dependents on the periodic
  resync (`reconcileInterval`, default 5m); there is no watch on Applications to
  unblock promptly. Candidate improvement: watch Applications, or requeue the
  blocked delete on the rate limiter instead of the full interval.
- **F2** — The `upgrading` phase is set in-memory but never persisted on a
  successful upgrade (single end-of-reconcile status patch). Either persist an
  interim status or treat `upgrading` as internal-only and document it.
- **F3 (env)** — Rapid same-name addon churn leaves orphaned ResourceTrackers
  (KubeVela GC race); public-registry versions drift in CUE-compat. The e2e
  mitigates both via the local mock + unique addon names per `It`.
