# KEP-2.13 Addon Dependencies as First-Class Addon CRs

**Date:** 2026-06-22
**Branch:** `feat/kep-2.13-addon-types`
**Status:** Draft (expected to change as we refine)
**Builds on:** the KEP-2.13 Addon CRD controller already on this branch (reconcile/install/status/deletion).

## Goal

When an Addon CR is enabled and its package declares dependencies, each dependency becomes its own first-class Addon CR with its own version, status, drift detection, and deletion lifecycle, instead of a bare `addon-<dep>` Application created as a side effect. No new stored state. Reuse the existing enable and disable machinery.

## Background: how dependencies work today

The CLI/imperative path already installs dependencies, but not as CRs:

- `installDependency` (`addon.go:1025`, reads the dependency list at `addon.go:1050`) builds a full Installer copy (`depHandler := *h`) and calls `depHandler.enableAddon` (`addon.go:1080`/`1107`) for each dependency. That is the same `enableAddon` used for a top-level addon, so the dependency gets a complete install: definitions rendered, `addon-<dep>` Application created via `createOrUpdate`, defs/schemas applied.
- The dependency's Application carries the addon identity labels `oam.LabelAddonName` and `oam.LabelAddonVersion` (`render.go:265-266`), which is why `vela addon status <dep>` works (`GetAddonStatus` → `FetchAddonRelatedApp`, `addon.go:1734`).
- But the dependency gets no Addon CR. In the declarative model that means no CR-level drift detection, status, or lifecycle for it.

Two existing behaviors we deliberately reuse rather than reinvent:

1. **Deletion protection is computed on demand, not stored.** `DisableAddon` (`helper.go:68`) with `force=false` calls `checkAddonHasBeenUsed` (`utils.go`), which lists every Application cluster-wide, computes the definitions the addon created, and flags any Application whose components/traits/workflow-steps/policies reference them. Because a dependent addon's own Application uses the dependency's definitions (for example `addon-velero` uses fluxcd's `helm` component type), this already blocks deleting a still-needed dependency, including addon-to-addon. Our Protect deletion path (`handleDeletion` → `disable(force=false)` → `DisableAddon`) already runs this. So a required-by set is unnecessary.
2. **No cascade delete.** `vela addon disable dex` deletes only `addon-dex` and leaves velaux and fluxcd running. We keep that: deleting a parent does not delete its dependencies.

## Reconcile flow for a parent (for example velero)

The controller does this before it installs the parent itself:

1. Read the package's `metadata.dependencies` (the same list `installDependency` reads at `addon.go:1050`).
2. For each dependency, resolve the version with the existing `calculateDependencyVersionToInstall` (`addon.go:1148`), then ensure an Addon CR exists for it:
   - If none exists, create one with `spec.version` set to the resolved version, the registry inherited from the parent, and an annotation `addon.oam.dev/auto-created=true` marking provenance.
   - If a CR already exists (user-made or made by a previous parent), adopt it and do not duplicate.
   - If the existing dependency CR's version does not satisfy this parent's constraint, do not mutate the shared dependency; set a `DependencyVersionConflict` condition on the parent and stop.
3. Gate on readiness: if any dependency CR is not yet phase `running`, set the parent to phase `installing` with a `DependenciesNotReady` condition and requeue. The parent does not call install while a dependency is not ready.
4. Once every dependency CR reports `running`, install the parent through `EnableAddon`, passing a new option `SkipInstallDependency` so `EnableAddon` does not also install dependencies imperatively. The dependency CRs own that now, which avoids a double install.

## Version selection semantics

Reuse `calculateDependencyVersionToInstall` (`addon.go:1148`) unchanged. Its rule:

- Dependency already installed: with no constraint, keep the installed version; with a constraint, keep it if `checkSemVer(installedVersion, constraint)` passes.
- Dependency not installed: with no constraint, latest available; with a constraint, the newest available version that satisfies it.
- If an installed version does not satisfy a new parent's constraint, it returns an error rather than upgrading or downgrading a shared dependency.

The only new behavior is turning that conflict error into a `DependencyVersionConflict` status condition on the parent CR. The shared dependency is never mutated to satisfy a new parent, because it may be in use by many other addons (fluxcd is depended on by about 40 addons in the catalog). In practice conflicts are rare, because almost every catalog dependency is declared without a version.

## Drift

Every addon, parent or dependency, has its own Addon CR whose controller re-applies on the periodic resync (`defaultReconcileInterval`, `addon_controller.go:60`). fluxcd self-heals through fluxcd's own reconcile loop, the same way velero does through its own. Drift detection for dependencies falls out of making them real CRs; there is no separate dependency-drift code.

## Transitive chains

Because each dependency CR runs the same resolution step when it reconciles, a chain like `vector-config → loki → o11y-definitions → vela-prism` resolves one level per CR: vector-config's CR creates loki's CR, loki's CR creates o11y-definitions' CR, and so on. No recursion inside a single reconcile, and no special casing for depth. (Catalog dependency hubs verified: fluxcd ~40 dependents, terraform 10, o11y-definitions 4, crossplane 2, gateway-traits 2.)

## Deletion

Unchanged from what we already built. Deleting the parent CR runs `handleDeletion`, which deletes only the parent's own Application; dependency CRs are left running, matching `vela addon disable dex`. Deleting a dependency CR while a parent still uses it is blocked by the existing `checkAddonHasBeenUsed` scan (already wired through our Protect policy), because the parent's Application uses the dependency's definitions. Force and Orphan stay rejected by CEL.

## New and changed pieces

- `pkg/addon` `EnableAddon`: a new `SkipInstallDependency` InstallOption that short-circuits `installDependency`.
- The addon controller `Reconcile`: a dependency-resolution step that ensures or adopts dependency CRs and gates on them being `running` before installing the parent.
- `AddonStatus` conditions: two new reasons, `DependenciesNotReady` and `DependencyVersionConflict`. Optionally a small read-only status list of dependency names and their phases, for observability.
- A provenance annotation `addon.oam.dev/auto-created` on controller-created dependency CRs.

The only touch outside the controller package is the new `SkipInstallDependency` option in `pkg/addon`.

## Error handling

- Dependency addon not found in any registry: parent goes to `failed` with a `DependencyResolutionFailed` reason.
- Version conflict: parent stays `installing` with `DependencyVersionConflict`, dependency untouched.
- Dependency install failing or not yet ready: parent stays `installing` with `DependenciesNotReady` and requeues until the dependency recovers.

## Testing

- Unit tests on the resolution step: create-when-missing, adopt-when-present, version-conflict, and the readiness gate, using the existing controller test seams (`installFn`/`readBackFn`/`disableFn` plus a new dependency seam if needed).
- E2E against the cluster (extending `test/e2e-test/addon_crd_test.go`): enable a parent with a dependency (velero → fluxcd, or dex → velaux + fluxcd), assert the controller created the dependency CRs, the parent waited in `installing` until they were `running`, then the parent reached `running`. Assert deleting the parent leaves the dependency CRs. Assert deleting an in-use dependency is blocked.

## Out of scope / deferred

- Cascade delete of dependencies on parent removal (we keep current no-cascade behavior).
- A stored required-by set (the on-demand `checkAddonHasBeenUsed` scan covers deletion protection).
- Force/Orphan deletion flows (CEL-rejected today).
- Automatic upgrade of a shared dependency to satisfy a newer parent (conservative refuse + conflict condition instead).
