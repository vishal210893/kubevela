# KEP-2.13 Story 102617 — Reconcile Addon CR: fetch, install, report status

- **Jira**: GWCP-102617 (epic GWCP-100436, KEP-2.13 Declarative Addon Lifecycle, Slice 1)
- **Date**: 2026-06-15
- **Confluence**: parent implementation plan (3299770797) + child "how vela addon enable works today" (3300622479)
- **Status**: design approved

## Problem

The Addon reconciler skeleton (GWCP-102565) watches Addon CRs, honors the pause
label, and reschedules itself, but its `Reconcile` body is a TODO. This story fills
that body so applying an `Addon` CR produces the same on-cluster result as
`vela addon enable <name>` does today, driven server-side by the controller.

## Key insight

The install engine already exists: `pkg/addon.EnableAddon` (`pkg/addon/helper.go:55`).
`vela addon enable` calls it client-side. The controller calls the same function
server-side with the manager's client/applicator/rest.Config. We reuse the engine; we
do not rewrite it. The CLI-only parts (cobra flags, prompts, endpoint printing, the
blocking spinner) are dropped — "wait for running" becomes a status condition.

`EnableAddon` signature (verified):
```go
func EnableAddon(ctx context.Context, name, version string, cli client.Client,
    dc *discovery.DiscoveryClient, apply apply.Applicator, config *rest.Config,
    r Registry, args map[string]interface{}, cache *Cache, registries []Registry,
    opts ...InstallOption) (string, error)
```
Pass `cache = nil` so it fetches every reconcile (digest skip is out of scope).

## Scope boundary (locked)

In scope: status writers, source resolution + fetch, delegate install + own the
Application, report status. `Ready=True` means "EnableAddon returned nil" (simplified
terminal state).

Out of scope (later stories): drift correction / staleness diff; digest-based
skip-when-unchanged; health-gated running (waiting on the owned Application's own
readiness); finalizer + Force/Orphan deletion policies.

## Design

### File structure

The skeleton lives at `pkg/controller/core.oam.dev/v1beta1/addon/reconciler.go`. New
focused files in that package:

- `status.go` — status writers only. `setPhase`, `setCondition`, the
  `client.Status().Patch` wrapper with field manager `addon.oam.dev/controller`. No
  business logic.
- `install.go` — the thin adapter. Build `EnableAddon` inputs from the CR (registry via
  `NewRegistryDataStore`/`GetRegistry`, version, `spec.parameters`), call `EnableAddon`,
  read the result back (owned Application / `GetAddonStatus`) into status fields.
- `reconciler.go` — orchestration only. The phase machine wiring the two above in
  order, backoff on registry-unreachable, requeue.
- Tests: `status_test.go`, extended `reconciler_test.go`, and a delegate test (fake
  client or envtest).

(Deviation from the Confluence doc: it shows the helpers inside the `Reconcile`
function. The split into small files is a structuring choice; behaviour is identical.)

### Status writers (AC1–AC4)

- `setPhase(addon, phase)` sets `status.phase` and `status.lastReconciledAt` together.
- `setCondition(addon, type, status, reason, message)` writes a `metav1.Condition` with
  `ObservedGeneration = addon.Generation`, moving `lastTransitionTime` only when
  status/reason/message change vs the existing condition of that type. Use
  `meta.SetStatusCondition` semantics.
- All status writes go through `client.Status().Patch` with field manager
  `addon.oam.dev/controller`. Never patch spec. `status.observedGeneration` is updated
  each reconcile that mutates status.
- First reconcile of a non-deleting CR (phase empty): `phase: installing`,
  `Ready=False / Reconciling`.

### Source resolution + fetch (AC5–AC8)

- Resolve `spec.registry` via `NewRegistryDataStore`/`GetRegistry`; version-resolve +
  fetch happen inside `EnableAddon` (OCI/Git/OSS readers).
- Success → `SourceResolved=True`.
- Registry-unreachable → `SourceResolved=False`, reason `RegistryUnreachable`,
  actionable message, requeue with exponential backoff (initial 30s, capped 10m),
  **leave phase unchanged** (transient outage is not alarmist).
- Persistent failure beyond the backoff window → `phase: failed`, preserving the
  `SourceResolved=False` message. (From Jira AC8; the Confluence doc omits this.)

### Delegate install + own the Application (AC9–AC15)

- Thin adapter builds installer inputs (registry, version, `spec.parameters`).
- Set `phase: installing` on new install, `phase: upgrading` when `spec.version` differs
  from `status.installedVersion`, before delegating.
- `EnableAddon` creates/updates `addon-{name}` in vela-system with the
  `addons.oam.dev/name|version|registry` labels.
- After it returns, read the owned Application (or `GetAddonStatus`) and populate
  `status.applicationName`, `status.installedVersion`, `status.installedRegistry`.
- Success → `phase: running`, `Ready=True`.
- Idempotency (AC14): no spec change → no-op, server-side apply no churn, phase steady.
- No regression to `vela addon enable` (AC15).

### Reconcile flow

```
fetch CR; honor pause                         (skeleton, exists)
if phase == "":  installing + Ready=False/Reconciling   (status writers)
resolve registry
set phase installing|upgrading
info, err := EnableAddon(...)                 (fetch + install + own addon-{name})
  err == registry-unreachable -> SourceResolved=False/RegistryUnreachable,
                                  phase unchanged, backoff 30s..10m
                                  (past window -> failed)
  err != nil                   -> phase=failed, Ready=False
  err == nil                   -> SourceResolved=True, read back status,
                                  phase=running, Ready=True
requeue at interval
```

## Open decision (resolve in the plan)

Backoff mechanism. The Confluence doc phrases it as "requeue with exponential backoff."
Two implementations:
- **Return the error** and let controller-runtime's workqueue rate-limiter back off
  (cleaner, no manual state) — but the default limiter caps and shape may not match
  "30s initial, 10m cap" exactly, so it needs a configured rate limiter on the
  controller.
- **Manual `RequeueAfter`** with backoff tracked in status/annotation (matches the
  doc's literal phrasing, explicit control, more state to manage).

Recommendation: configure a per-controller exponential rate limiter (30s base, 10m cap)
and return the error, unless the team prefers explicit `RequeueAfter`. Decide in the
plan.

## Testing (AC16–AC18)

- Unit: phase transitions (installing→running, →failed, running→upgrading); idempotent
  condition writes (identical `setCondition` does not move `lastTransitionTime`);
  first-install vs upgrade phase selection; status fields populated; registry-unreachable
  backoff bounded and capped at 10m.
- Manual e2e (AC17): apply a pinned Addon CR; within ~60s `kubectl get addons` shows
  `running` with `status.installedVersion` set and the owned Application in vela-system.
- AC18: `go build`, `go vet`, `gofmt`, addon package tests green.
