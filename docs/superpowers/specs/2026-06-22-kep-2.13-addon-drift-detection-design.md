# KEP-2.13 Addon Drift Detection via ResourceTracker

**Date:** 2026-06-22
**Branch:** `feat/kep-2.13-addon-types`
**Status:** Draft (expected to change as we refine)
**Builds on:** the KEP-2.13 Addon CRD controller already on this branch (reconcile/install/status/deletion).

## Goal

Give the Addon CR explicit drift detection for everything it installs, healing deleted or edited resources from stored manifests, and call the expensive network `install()` (fetch + `EnableAddon`) only when the addon is completely missing (first install) or its `spec.version` changes. Steady-state reconciles do no network I/O.

## Background: the two packages and the gap

An addon install produces two categories of resources (`dispatchAddonResource` in `pkg/addon/addon.go`):

1. **The Application** (`addon-<name>`), created via `createOrUpdate`. KubeVela's own ResourceTracker and the Application controller already drift-detect everything inside it (the workloads it renders).
2. **Auxiliary resources applied directly by the installer** via `h.apply.Apply(...)` after `addOwner(o, app)`: definitions (`RenderDefinitions`), config templates (`RenderConfigTemplates`), definition schemas (`RenderDefinitionSchema`), velaQL views (`RenderViews`), the CUE `auxiliaryOutputs` from `RenderApp`, and the args secret (`RenderArgsSecret`). These carry an ownerReference to the Application for garbage collection only. The Application controller does not reconcile them, because they are not in the Application's component or output set.

Today the auxiliaries get healed only incidentally: the addon controller's `install()` re-runs `EnableAddon` every reconcile with a `nil` cache (`install.go:69`, "fetch every reconcile"), which re-applies them within the 5-minute resync. Two problems: that healing is tied to the wasteful re-fetch-and-re-apply, and if we ever make `install()` skip the re-apply when nothing changed, we lose the healing. Explicit drift detection fixes both.

## How the Application kind already does drift correction (the pattern we mirror)

`StateKeep` (`pkg/resourcekeeper/statekeep.go:41`) runs every Application reconcile. It walks the `ManagedResources` of the app's ResourceTrackers and, per resource:
- if `mr.Deleted`, deletes the live object if it still exists;
- otherwise decodes the stored manifest from `mr.Data.Raw` (`mr.ToUnstructuredWithData`) and re-applies it through `h.applicator.Apply` (`statekeep.go:106`).

The applicator does a three-way merge patch with an empty-patch short-circuit (`isEmptyPatch`), so one code path handles every case: a deleted resource is re-created, an edited resource is patched back to the stored desired state, an unchanged resource no-ops. There is no separate hash; the stored manifest is the source of truth and the merge patch is the comparison. None of it touches the network, because the desired manifest comes from the RT, not the registry. We mirror this exactly for the addon.

## Storage: an addon-owned ResourceTracker CR

`ResourceTrackerSpec.ManagedResources` is a list of `ManagedResource`, and `ManagedResource.Data` is a `runtime.RawExtension` (`raw`) holding the full object, with an optional `Compression` (`apis/core.oam.dev/v1beta1/resourcetracker_types.go`). The same type that backs Application drift stores the full manifests we need, plus compression for large addons.

We create one ResourceTracker per addon, owned by the Addon CR (via `controllerutil.SetControllerReference`), with addon labels (`oam.LabelAddonName`) and a marker that distinguishes it from an Application's RT. It records the Application object itself plus every auxiliary as `ManagedResources` with their rendered manifests.

**Open verification (spec-time):** confirm the Application's ResourceTracker garbage collector (the `resourcetracker` controller and the app's RT GC) ignores an addon-owned RT. The app RT GC keys off Application ownership / app labels; an addon-owned RT must not carry those, so it is never collected as an orphaned app RT. If reuse turns out to entangle with the app RT GC, fall back to a dedicated addon-owned holder using the same `ManagedResource` shape (decision recorded in the dependency/earlier brainstorm as the runner-up).

## Reconcile control flow for a live addon

1. Decide whether a full install is needed. `needsInstall` is true only when:
   - there is no addon ResourceTracker yet (first install, the "completely missing" case), or
   - `spec.version` differs from `status.installedVersion` (an upgrade, which genuinely needs new manifests from the registry).
2. If `needsInstall`: call `install()` as today (network fetch + apply through `EnableAddon`). Then capture the rendered Application and all auxiliaries and write or refresh the addon's ResourceTracker (`ManagedResources` with `raw` manifests). Set phase `running`.
3. Otherwise (steady state, no network): load the addon ResourceTracker and run the heal loop. For each `ManagedResource`, decode `mr.Data.Raw` and re-apply through `apply.Apply` with the addon's ownership guards (mirroring `StateKeep`, using options like `apply.DisableUpdateAnnotation()` as the existing addon apply does). The Application's own children stay the Application controller's job; the addon re-applies only the Application object and the auxiliaries.
4. Deletion is unchanged. `handleDeletion` runs the Protect/Force/Orphan policy; the addon ResourceTracker and its tracked resources are cleaned up alongside the addon (owner reference plus the existing disable path).

**Capturing manifests for the RT:** `RenderApp` (`render.go`) already returns the Application and the auxiliary outputs, and `dispatchAddonResource` assembles `defs + templates + schemas + views`. The capture step collects the same set the installer applies and serializes each into a `ManagedResource`. The implementer wires the capture either by having `dispatchAddonResource` return the applied object list or by re-rendering deterministically from the install package held in memory during `install()` (no extra fetch).

## What this enables

- Deleting an auxiliary (a definition, schema, or view) is healed on the next reconcile from the stored manifest, with no network call.
- Deleting the Application is healed from the stored manifest too (the RT records the Application object), so "someone deleted everything but the RT survives" still needs no network.
- The network only returns when the ResourceTracker itself is gone (true first install) or on a version change.
- It removes the dependence on re-fetch-and-re-apply every reconcile, so the wasteful blind re-apply can be dropped.

## New and changed pieces

- The addon controller `Reconcile` / `install.go`: a `needsInstall` decision, a manifest-capture step after a successful install, and a `stateKeep`-style heal loop that runs when no install is needed.
- A small package for the addon ResourceTracker: create/refresh (write `ManagedResources`), load, and heal (decode + `apply.Apply`).
- `EnableAddon` reuse unchanged for the install path; the heal path does not call it.
- Status: a condition reason for drift healing is optional; phase stays `running` while healing.

## Error handling

- RT read/parse failure: requeue with backoff; do not fall back to a network install purely because the RT could not be read (avoid masking a transient API error as a "complete miss").
- A single resource failing to re-apply: record and continue with the rest (aggregate errors, like `StateKeep`), then requeue.
- A genuinely empty/absent RT: treated as first install (`needsInstall`).

## Testing

- Unit tests on the heal loop: missing-resource recreation, in-place-edit correction, no-op when clean, aggregate-error on partial failure, using the existing controller test seams and a fake client with a pre-populated addon RT.
- Unit test on `needsInstall`: no RT -> install; version change -> install; RT present and version equal -> heal path (no install call), asserted via the `installFn` seam not being invoked.
- E2E against the cluster (extending `test/e2e-test/addon_crd_test.go`): install an addon, delete one auxiliary (a definition) and the owned Application, assert both are restored without a registry fetch (mock registry hit-count or controller logs show no fetch), and assert a `spec.version` bump does trigger a fetch.

## Out of scope / deferred

- Multicluster fan-out of the heal loop (the addon controller currently reconciles local; match existing addon behavior).
- Hash-based change tracking (the re-apply + empty-patch approach makes a stored hash unnecessary).
- Dropping the blind re-apply in `EnableAddon` itself; this design makes it safe to do later but does not require changing `EnableAddon`'s internals in this change.
