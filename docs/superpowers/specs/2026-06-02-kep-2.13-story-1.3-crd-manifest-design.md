# KEP-2.13 Story 1.3 — Generate Addon CRD manifest and wire into Helm chart

- **Jira**: GWCP-101810 (part 3 of epic GWCP-100436 — KubeVela KEP-2.13 Declarative Addon Lifecycle)
- **Date**: 2026-06-02
- **Branch**: `feat/kep-2.13-addon-types` (stacks on stories 1.1 and 1.2)
- **Status**: design approved

## Problem

Stories 1.1 and 1.2 defined the Go `Addon` type, its kubebuilder markers, and the
full `AddonStatus` struct. That is source code the cluster never sees. This story
compiles the type into the CRD YAML the API server enforces, ensures that artifact
ships inside the vela-core Helm chart, and surfaces useful at-a-glance state through
`kubectl get addons`.

The generated CRD already declares `scope: Cluster`, `shortNames: [addon]`, and the
`status` subresource (from story 1.1 markers). The gap: story 1.1 did **not** add
`+kubebuilder:printcolumn` markers, so the generated CRD has no
`additionalPrinterColumns`. AC3 requires three.

## Scope

In scope:
- Add three `+kubebuilder:printcolumn` markers to the `Addon` type.
- Regenerate the CRD so `charts/vela-core/crds/core.oam.dev_addons.yaml` carries the
  printer columns.
- Verify ACs, including a live k3d install → apply → `kubectl get` → delete smoke loop.

Out of scope (other stories under GWCP-100436):
- CEL admission validation on `spec.version` / `spec.deletionPolicy` (story 1.4 —
  regenerates this same manifest with extra validation, so 1.3 lands the structural
  manifest first to avoid churn).
- RBAC manifests for the addon controller.
- Controller deployment.

## Design

### 1. Source edit — printer columns

Add to `apis/core.oam.dev/v1beta1/addon_types.go`, directly above the existing
`+kubebuilder:object:root=true` block (~line 93), mirroring the `Application` type
(`application_types.go:73-78`):

```go
// +kubebuilder:printcolumn:name="PHASE",type=string,JSONPath=`.status.phase`
// +kubebuilder:printcolumn:name="VERSION",type=string,JSONPath=`.status.installedVersion`
// +kubebuilder:printcolumn:name="AGE",type=date,JSONPath=".metadata.creationTimestamp"
```

JSON tags confirmed present: `status.phase` (line 172), `status.installedVersion`
(line 186). `type=date` on AGE makes kubectl render relative time (`5m`, `3d`). This
is the only source change.

### 2. Generation strategy (container-aware)

Canonical target is `make manifests` (`Makefile:106-112`), which chains
`tidy installcue kustomize sync-crds`, `go generate`, a kustomize merge, the dispatch
step, and `gen_definitions.sh`. It needs network (`go mod download` in `sync-crds`)
and can OOM on this constrained dev container.

- **Primary**: run `make manifests`.
- **Fallback (identical artifact for our CRD)**: run only the two steps that touch the
  addon CRD —
  1. `(cd apis && go generate ./...)` → controller-gen writes
     `config/crd/base/core.oam.dev_addons.yaml`.
  2. `go run ./hack/crd/dispatch/dispatch.go config/crd/base charts/vela-core/crds`
     → copies it into the chart.
- After either path, `git restore` the unrelated cross-package formatting noise in
  `apis/core.oam.dev/{common,condition,v1alpha1}/zz_generated.deepcopy.go` if it
  appears (controller-gen version drift; not part of this PR).

### 3. Chart wiring

No manual wiring. `dispatch.go` walks `config/crd/base/`, derives the resource name
from the filename (`extractMainInfo` splits on `_` then `.`), and copies each CRD into
`charts/vela-core/crds/`. The addon CRD lands automatically. Helm installs it via the
`crds/` convention (raw YAML, installed once before templates, not templated). No
`charts/vela-core/kustomization.yaml` — the chart does not use kustomize, and AC4 is
satisfied via the Helm path.

### 4. Verification

- **AC1 (idempotency)**: generate twice, compare (MD5 / `git diff`). Expect no change.
- **AC2**: assert `scope: Cluster`, `names.shortNames: [addon]`,
  `subresources.status: {}` in the generated file (already present; re-confirm).
- **AC3**: assert three `additionalPrinterColumns` (PHASE / VERSION / AGE) render with
  the correct jsonPath and AGE `type: date`.
- **AC4 / AC5 / AC6 (live k3d smoke)**:
  1. `k3d cluster create` a throwaway cluster.
  2. Install the CRD: `helm template charts/vela-core | kubectl apply -f -`, or a
     targeted `kubectl apply -f charts/vela-core/crds/core.oam.dev_addons.yaml`.
  3. `kubectl apply` an example `Addon` with minimum required fields.
  4. `kubectl get addons.core.oam.dev` shows PHASE / VERSION / AGE.
  5. Delete the CR and `kubectl delete crd addons.core.oam.dev` — clean, no stuck
     finalizers (no controller running yet to add one). **Note**: Helm's `crds/` are
     not removed on `helm uninstall` by design; clean removal is via explicit
     `kubectl delete crd`, which is what AC6 actually exercises.
  6. Tear down the cluster.
- **AC7**: `go vet ./apis/...`; flag `make verify` / `manifests-check` as the upstream
  CI gate (run if feasible in-container, otherwise validate in the dev env).

## Deliverables

- 1 source edit: `apis/core.oam.dev/v1beta1/addon_types.go` (3 marker lines).
- 1 regenerated tracked file: `charts/vela-core/crds/core.oam.dev_addons.yaml`.
- 1 throwaway example Addon manifest for the smoke test (not committed unless wanted).

## Risks / notes

- Full `make manifests` may fail in-container (network/OOM/linker); the fallback path
  produces the same `charts/vela-core/crds/core.oam.dev_addons.yaml`.
- Generated-output determinism depends on the pinned controller-gen version; commit the
  exact output and revert cross-package noise so the CI manifests-check stays green.
- AC4's `kubectl apply -k charts/vela-core` wording is inaccurate (no kustomization in
  the chart); satisfied via the Helm path instead.
