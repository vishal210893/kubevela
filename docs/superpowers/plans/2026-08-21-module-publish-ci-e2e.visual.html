Objective

Make CI prove the `vela module publish` path against a real OCI registry, and add one e2e test that walks the whole loop: build a module artifact, publish it, fetch it, deploy it.

**Done means:** a CI job runs the `-tags integration` tests against a live `registry:2` daemon with no subtest silently skipping, and a Ginkgo spec publishes a module from the runner into an in-cluster registry and deploys it through the controller.

**Scope is coverage only.** The publish feature itself is complete and staged; its design lives in `docs/superpowers/specs/2026-08-20-module-publish-design.md`. Nothing in this plan changes product behavior.

**Stack:** Go 1.23, Ginkgo/Gomega, GitHub Actions, kind, helm, `registry:2`.

The e2e goes further and proves the controller can fetch what the CLI published.

Why the e2e registry runs inside the cluster

The runner and the pods do not share a reachable address for the same registry, and that asymmetry decides the whole shape of Task 3. A docker container on the host network is reachable from the kind node but not from pods, so a host-side registry cannot serve the controller. An in-cluster Service can serve the controller but its DNS name does not resolve on the runner.

So the registry lives in the cluster, and each side reaches it by its own path: the runner publishes through a `kubectl port-forward`, and the controller fetches over the Service DNS name. Both names point at the same artifact, which is exactly what the test needs to prove.

Files

Task 1 — CI job for the tagged integration tests

Modifies `.github/workflows/unit-test.yml` only. It consumes two existing test files: `pkg/module/publish_integration_test.go`, which runs an in-process registry and needs nothing external, and `pkg/module/service/fetch_integration_test.go`, whose `oci` subtest reads `MODULE_OCI_REGISTRY`.

Read the existing workflow in full first and match its style — the same action versions with their pinned SHAs, the same Go setup, the same job-level `if` guards.

**The failure mode here is a green job that proves nothing.** Without `MODULE_OCI_REGISTRY`, the `oci` subtest of `TestFetchModule_RoundTrip` skips silently and the job still passes. The `registry:2` service container plus that env var are what make it actually run. Conversely, `MODULE_ECR_REGISTRY` must stay unset so `TestPublishRoundTripECR` skips — ECR is deliberately not a CI dependency.

Task 2 — A definitions-only module fixture

The fixture must satisfy the package format `pkg/module.ParseModule` enforces: `_module.cue` carrying `module` and `version` (strict semver, no leading `v`), one `v<N>/` directory per line with a `_version.cue` carrying `apiVersion`, and a non-empty `v<N>/definitions/`.

Its identity is fixed here and used verbatim in Task 3's assertions: module `e2e-widget`, version `1.0.0`.

`v1/definitions/widget.cue` must be a ComponentDefinition that KubeVela's own renderer accepts, since `pkg/module/parse.go` renders `.cue` definitions through `definition.Definition.FromCUEString`. Model it on an existing internal definition — `vela-templates/definitions/internal/component/webservice.cue` is the reference — but keep it minimal: a `ComponentDefinition` named `e2e-widget` whose template outputs a single ConfigMap. A ConfigMap keeps the deploy leg free of image pulls and readiness waits.

The exact CUE is deliberately not written out here. It has to satisfy the definition renderer, and that shape belongs to whoever is reading `webservice.cue` alongside it.

Do **not** add `auxiliary/xrd.yaml` or `v1/auxiliary/composition.yaml`. Those are Crossplane types, the e2e cluster has no Crossplane CRDs, and a definitions-only module is what makes the deploy leg assert something real.

**Verify:** write a throwaway program under `/tmp` (do not commit it) that calls `module.ParseModuleDir` and `module.PackageModule` on the fixture path and prints the module name, version, lines, and the archive's file list. Confirm the parse succeeds, the line `v1` is present and enabled, and the definition rendered with a non-empty `metadata.name`.

A `render definition widget.cue: ...` error means the CUE does not satisfy KubeVela's renderer. Fix the CUE, not the parser.

Then `git add test/e2e-test/testdata/module/e2e-widget`.

Task 3 — The full-flow e2e test

Consumes the Task 2 fixture, the `vela` binary the e2e job puts at `bin/vela`, and the `module` ComponentDefinition the chart installs.

`test/e2e-test/testdata/module/registry.yaml` holds a `Deployment` named `oci-registry` running `docker.io/library/registry:2` on container port 5000, plus a `Service` named `oci-registry` exposing port 5000, both in the `default` namespace. Keep it plain: no persistence, no auth, no TLS.

Before writing the spec, read the conventions of the suite you are joining. `test/e2e-test/helmchart_test.go` stands up zot from `testdata/auth/manifests/zot.yaml`, so it is the closest precedent for bringing up a registry; `test/e2e-test/definition_test.go` is a smaller spec worth reading for how it gets a client, namespaces its resources, and waits. Follow those patterns rather than inventing new ones.

  • [ ] Apply testdata/module/registry.yaml; wait for the oci-registry Deployment to be Available
  • [ ] Start kubectl port-forward svc/oci-registry 5000:5000 as a child process
  • [ ] Publish with the positional-reference form, which needs no registry entry
  • [ ] Assert the artifact is really in the registry over HTTP
  • [ ] Assert immutability against the live registry
  • [ ] Register the in-cluster URL — the one the controller can resolve
  • [ ] Deploy through the controller
  • [ ] Assert the outcome in the cluster
  • [ ] DeferCleanup: delete the deploy Application, the registry entry, and the registry manifest

Give the deploy wait a generous but bounded timeout — 5 minutes matches the CLI's own default — and let failures print the CLI's combined output. A bare `exit status 1` in CI is unactionable.

**Verify:** `go vet ./test/e2e-test/` must be clean, and `CGO_ENABLED=0 go test -run XXX -count=1 ./test/e2e-test/` must build without running specs.

**Wiring:** `makefiles/e2e.mk`'s `e2e-test` target runs `ginkgo -v ./test/e2e-test`, naming the directory rather than individual specs, so a new file is picked up with no change. Confirm by reading the target and say so in the report; only edit it if the suite is filtered by label or focus.

Then `git add test/e2e-test/module_publish_test.go test/e2e-test/testdata/module/registry.yaml`.

**Task 3 cannot run in this devcontainer, and no report should claim otherwise.** It needs the controller built from this source — the module render provider is not in any published image — and that needs a docker daemon, which is absent here. Its first real execution will be in CI, and that run may need one round of fixes. Do not attempt to run it locally; state the gap plainly instead.

Coverage check

Unit tests are already present and untagged, so they already run in CI. Task 1 adds the OCI integration job. Tasks 2 and 3 add the full create-publish-fetch-deploy flow. ECR appears nowhere in CI, per the explicit constraint.

Type consistency holds across tasks: the fixture's module name `e2e-widget` and version `1.0.0` are fixed in Task 2 and used verbatim in Task 3's assertions, and the registry Service name `oci-registry` and port 5000 are fixed in Task 3's manifest and reused in its port-forward and registry-add steps.
