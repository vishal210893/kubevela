checkWorkflowRestart and valuesfrom_fingerprint.go

Notes for someone reading this code for the first time. All line numbers are against current master.

TL;DR

If you edit a ConfigMap or Secret that a helmchart references through valuesFrom, KubeVela needs some way to notice and restart the workflow. It does this by hashing the referenced content on every reconcile and sticking the hash onto the Application's revision string as a -vf-<hex> suffix. When the content changes, the hash changes, the suffix changes, and the gate that compares revisions fails. The workflow restarts.

Two files share the work. workflow.go owns the gate logic. valuesfrom_fingerprint.go computes the hash. They live in the same package, but only one direction of dependency exists: workflow.go imports the fingerprint, not the other way around.

Two fingerprints, don't confuse them

The codebase has two functions with "fingerprint" in the name. They live in different layers and do different jobs. New readers conflate them. Don't.

valuesfrom_fingerprint.go helm.go · computeReleaseFingerprint
Layer Controller (pkg/controller/.../application/) Helm provider (pkg/cue/cuex/providers/helm/)
Called by checkWorkflowRestart in workflow.go installOrUpgradeChart in helm.go itself
Hashes what Content of referenced ConfigMaps and Secrets (chart version, sha256 of values map)
Decides Whether to restart the workflow Whether to skip a helm upgrade API call
Stamps onto app.Status.Workflow.AppRevision as -vf-<hex> In-memory cache + cluster release fingerprint label

The controller fingerprint is the trigger: did anything content-wise change that should make us re-run? The helm fingerprint is the brake: now that we're re-running, does helm actually need to upgrade the release? They never call each other. They share no code. They're at different layers of the stack on purpose.

If you found yourself wondering whether valuesfrom_fingerprint.go is called from helm.go, the answer is no. Only workflow.go calls it. A grep confirms it: one non-test caller at workflow.go:195.

Where the gate gets called from

The reconciler in application_controller.go calls two helpers that live in workflow.go. They sound similar, but they handle unrelated things.

WhereFunctionWhat it actually does
application_controller.go:151 handleWorkflowRestartAnnotation Reads the app.oam.dev/restart-workflow annotation and copies it into a status field. Just an annotation parser. Don't get distracted.
application_controller.go:220 checkWorkflowRestart The actual gate. This is where the valuesFrom fingerprint plugs in.

If you're trying to find "where does the controller decide to re-run a workflow when a CM is edited," the answer is the second one, line 220.

Reconcile order

Within a single reconcile pass, the order matters in two specific ways:

┌─────────────────────────────────────────────┐ │ Reconcile(req) │ │ │ │ L116 Get(app) │ │ L126 if Paused → return │ │ L145 NewAppHandler(...) │ │ L151 handleWorkflowRestartAnnotation() │ annotation → status field │ L153 handleFinalizers() │ │ L165 ApplyApplicationScopeTransforms() │ │ L180 GenerateAppFile() │ │ L188 PrepareCurrentAppRevision() │ builds handler.currentAppRev │ L194 FinalizeAndApplyAppRevision() │ │ L211 ApplyPolicies() │ │ L220 checkWorkflowRestart() │ ← the gate runs here │ L222 GenerateApplicationSteps() │ │ L236 workflowExecutor.ExecuteRunners() │ reads (possibly wiped) status │ L264 app.Status.Workflow = ... │ │ gcResourceTrackers / requeue │ └─────────────────────────────────────────────┘

Two ordering rules to keep in mind:

PrepareCurrentAppRevision at line 188 has to run before the gate. It populates handler.currentAppRev.Name, which is the spec-derived hash that becomes the base of desiredRev. If you ever wonder why desiredRev is non-empty by the time the gate runs, that's why.

The executor at line 236 has to run after the gate. The gate's job is to wipe app.Status.Workflow when a restart is needed. The executor reads that wiped status and starts from step zero. The two are sequential within the reconcile, so there's no concurrency concern.

Inside checkWorkflowRestart

The function packs four restart triggers into one body. It looks tangled at first. Here's the breakdown.

checkWorkflowRestart(ctx, app, handler): ┌── trigger 1: scheduled restart ──────────────────────────────────┐ │ L106 if app.Status.WorkflowRestartScheduledAt != nil: │ │ L109 if not yet time → return │ │ L113 if workflow not finished → return │ │ L127 clear scheduledAt │ │ L143 wipe Services / AppliedResources / Conditions │ │ L155 Workflow = {AppRevision: handler.currentAppRev.Name} │ │ L158 return ← the scheduled path EXITS here │ └──────────────────────────────────────────────────────────────────┘ ┌── triggers 2 + 3 + 4: revision-based restart ────────────────────┐ │ L162 desiredRev = handler.currentAppRev.Name │ trigger 3 (spec hash) │ L163 currentRev = app.Status.Workflow.AppRevision (or "") │ │ L166 publishVersionPinned = HasAnnotation(...PublishVersion) │ │ L168 if publishVersionPinned: │ │ L168 desiredRev = annotation value │ trigger 2 (publishVersion) │ L170 else: trim ":<hash>" off currentRev (legacy compat) │ │ │ │ L194 if NOT publishVersionPinned: │ trigger 4 starts │ L195 vfFp, err = computeValuesFromContentFingerprint(...) │ ← FINGERPRINT CALL │ L196 if err: │ │ L197 log V(2) — "fingerprint failed, falling back" │ │ L198 if currentRev starts with "<base>-vf-": reuse it │ stickiness fallback │ L201 elif vfFp != "": │ │ L202 desiredRev += "-vf-" + vfFp[:32] │ ← THE SUFFIX │ │ │ L206 if currentRev != "" && desiredRev == currentRev: │ │ L207 return ← gate passes, workflow keeps its state │ │ │ │ L211 wipe (same as trigger 1) │ │ L234 Workflow = {AppRevision: desiredRev} │ └──────────────────────────────────────────────────────────────────┘

The first block (the early return on WorkflowRestartScheduledAt) has nothing to do with valuesFrom. It only fires when a user has scheduled a restart through the annotation handler. You can read past it.

The second block is where the work happens. desiredRev starts as the spec-derived name. Then publishVersion overrides it (if pinned), or the valuesFrom fingerprint suffixes it (if not pinned and any helmchart component declares valuesFrom). currentRev comes from whatever was written last reconcile, possibly with its own -vf- suffix already attached.

The string comparison at line 206 is the whole gate. If the strings match, return. If not, wipe status and stamp the new revision.

Inside valuesfrom_fingerprint.go

The fingerprint file is small on purpose. It exposes one function and two constants. workflow.go imports those three things and nothing else.

What the file does NOT know about: Reconciler, AppHandler, Status.Workflow, desiredRev, publishVersion, the gate logic. None of it. That's all upstream.

What the file DOES know about: walking helmchart components on the Application, parsing a minimal struct out of their properties, reading the referenced ConfigMaps and Secrets, canonicalising the YAML, and hashing the result.

The narrowness is the point. You can unit-test the hash function without standing up a controller. You can unit-test the gate by handing it a precomputed app and handler. Each side fails or succeeds in isolation.

computeValuesFromContentFingerprint(ctx, app) (string, error): L101 if app == nil || no components → return "", nil L106 for each component: L107 if ctx.Err() → return "" (cancellation respected) L110 if comp.Type != "helmchart" → skip (only helmchart opts in) L113 if comp.Properties == nil → skip L117 json.Unmarshal(props.Raw, &helmchartProperties) L122 on parse error → SKIP this component (do not fail) L123 if no valuesFrom on this component → skip L126 releaseNamespace = props.Release.Namespace || app.Namespace L130 for each ref in props.ValuesFrom: L131 append resolvedRef{ref, app.Namespace, releaseNamespace} L139 if no refs collected → return "", nil (no opt-in → no suffix) L143 for each resolvedRef: L145 line, err = hashOneSource(...) L147 on error → return "", err (fail-loud here) L149 append line L151 sort.Strings(lines) (order-stable) L152 return sha256(join(lines, "\n"))

Three return shapes, three behaviours in workflow.go:

ReturnWhat it meansWorkflow.go reaction
"", nil App has no helmchart with valuesFrom Suffix not applied. App behaves as if this PR didn't exist.
"<hex>", nil Content hashed successfully Suffix appended at L202.
"", err API hiccup, parse error, cross-namespace reject Logged at V(2). Reuses prior -vf- suffix from currentRev if present, so the gate doesn't flap.

How one entry is hashed

For each valuesFrom entry, hashOneSource at lines 167-235 emits one line in the aggregate:

ConfigMap:default/podinfo-values/values.yaml=9f2a4c1b0d3e...
Secret:default/podinfo-overlay/values.yaml=<missing>

If the resource is found and the key exists, you get the hex digest. If the resource is missing and optional: true, you get the literal <missing> placeholder. The line is still emitted, so the aggregate hash stays stable while the resource is absent. The moment the resource shows up, the line flips to a real digest, and the aggregate moves.

If the resource is missing and not optional, the function returns an error. workflow.go then falls back to whatever suffix was already in currentRev, so a transient kube-API blip doesn't flap the revision.

canonicalLine at lines 245-259 is the part that makes the hash edit-stable:

var parsed map[string]interface{}
yaml.Unmarshal(raw, &parsed)         // tolerate YAML quirks
canonical, _ := json.Marshal(parsed) // sorted keys, no whitespace
h := sha256.Sum256(canonical)
return fmt.Sprintf("%s:%s/%s/%s=%s", kind, ns, name, key, hex(h)), nil
Edit-stability

Whitespace edits, comment edits, and key reordering inside the ConfigMap don't move the digest. Only semantic content changes do. That's because the YAML is parsed and then re-marshalled as JSON with sorted keys before hashing. Cosmetic edits round-trip back to the same bytes.

The duplicated cross-namespace rule

The cross-namespace check exists in two places. Once in helm.go as resolveValuesFromNamespace at helm.go:650, and once in valuesfrom_fingerprint.go as resolveNamespace at lines 274-283. Same rule both times:

Input namespaceResult
emptyrelease namespace
matches release nsrelease ns
matches app nsapp ns
anything elseerror (cross-tenant attempt)
Why the duplication

The helm provider lives under pkg/cue/cuex/providers/helm, which pulls in CUE, the helm SDK, and chart fetching. Importing any of that into the controller would create a circular dependency and bloat. So the rule was copied. There's a comment at line 269 calling this out. If you change the rule in one place, change it in the other. No compile-time guard exists.

Why the uncached client

hashOneSource at line 177 calls singleton.KubeClient.Get() directly. That's the uncached client, not the controller-runtime cached client.

The reason matters for production sizing. The cached client registers an informer for whatever type you Get. The first time you read a ConfigMap through it, you've registered a cluster-wide ConfigMap informer. The controller's memory now holds every ConfigMap in the cluster. Same for Secrets. That's not a trade we want.

The cost we pay instead is one direct API read per valuesFrom source per reconcile. For a typical app with one or two valuesFrom entries reconciling every five minutes, that's nothing. The comment at lines 162-166 spells this out.

Who owns what

┌──────────────────────────────────────────────────────────────────┐ │ workflow.go (the orchestrator) │ │ │ │ Owns: │ │ • the gate (desiredRev == currentRev short-circuit) │ │ • publishVersion suppression │ │ • stickiness fallback on transient errors │ │ • status wipe + new revision stamping │ │ • the four restart triggers │ │ │ │ Imports from valuesfrom_fingerprint.go: │ │ ─ computeValuesFromContentFingerprint(...) │ │ ─ valuesFromSuffixSeparator │ │ ─ valuesFromSuffixHexLen │ └──────────────────────────────────────────────────────────────────┘ │ ▼ function call only — no shared state ┌──────────────────────────────────────────────────────────────────┐ │ valuesfrom_fingerprint.go (the calculator) │ │ │ │ Owns: │ │ • walking helmchart components │ │ • parsing a minimal helmchartProperties shape │ │ • the duplicated cross-namespace rule │ │ • reading CM/Secret content (uncached client) │ │ • optional handling (<missing> sentinel) │ │ • YAML→JSON canonicalisation │ │ • sha256 + sort + hex │ │ │ │ Knows nothing about: │ │ • desiredRev / currentRev / status.Workflow │ │ • the gate logic │ │ • publishVersion │ │ • Reconciler / AppHandler │ └──────────────────────────────────────────────────────────────────┘

The coupling is one-directional and minimal. workflow.go calls one function and uses two constants. There's no shared state, no shared types beyond the function signature. If you wanted to swap the fingerprint algorithm tomorrow, you'd touch one file.

A walkthrough of one CM edit

Suppose you've applied localtest/helm-job-workflow-restart-test.yaml. Here's what each reconcile actually does.

T=0 user kubectl applies the manifest Reconcile #1: PrepareCurrentAppRevision → currentAppRev.Name = "cm-fingerprint-test-v1-<hash>" checkWorkflowRestart: desiredRev := "cm-fingerprint-test-v1-<hash>" currentRev := "" (status.Workflow is nil) computeValuesFromContentFingerprint → "9f2a4c..." desiredRev := desiredRev + "-vf-" + "9f2a4c1b0d3e..."[:32] gate: currentRev == "" → fall through (early-return needs both sides set) wipe + stamp: app.Status.Workflow = {AppRevision: desiredRev} ExecuteRunners → all 3 steps run for the first time T=2m Reconcile #2 (periodic resync, no changes): checkWorkflowRestart: desiredRev := same base name currentRev := same "-vf-9f2a4c..." (from status) computeValuesFromContentFingerprint → "9f2a4c..." (CM unchanged) desiredRev := same suffix gate: desiredRev == currentRev → RETURN (no-op) ExecuteRunners sees existing step status → all steps already complete T=5m user: kubectl patch configmap cm-fingerprint-test-values ... (controller doesn't see this — CM watch isn't wired) T=10m Reconcile #3 (next periodic resync): checkWorkflowRestart: desiredRev := same base name currentRev := "-vf-9f2a4c..." computeValuesFromContentFingerprint → "8b1d3e..." ← MOVED desiredRev := base + "-vf-8b1d3e..."[:32] gate: desiredRev != currentRev → fall through wipe + stamp: app.Status.Workflow = {AppRevision: desiredRev (new)} ExecuteRunners sees no step status → re-runs all 3 steps: stamp-when-ran → status updated apply-job → renders identical Job → 3-way merge no-op apply-helm → renders new values → helm upgrade fires → rev 2

Three reconciles. Two were no-ops at the gate. The third was a state wipe and a full workflow re-run. The CM edit sat in the cluster for five minutes between when the user made it and when KubeVela reacted to it. That gap is the periodic resync interval, and it's what Ayush flagged as a follow-up issue (configurable resync rate at the app level).
