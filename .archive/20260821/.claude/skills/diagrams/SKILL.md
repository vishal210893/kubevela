# Architecture Diagrams

This skill provides comprehensive architecture documentation through PlantUML diagrams. It supports 12 diagram types, operates in 4 modes, applies Guidewire enterprise theming, and tracks diagrams via a manifest system.

## CRITICAL RULES -- Read Before Generating Any Diagram

These rules are **mandatory** for every `.puml` file generated by this skill. Violating any of them produces diagrams that fail to render in online tools, CI pipelines, or environments without Graphviz installed.

1. **ALWAYS add `!pragma layout smetana` immediately after `@startuml`.**
   This tells PlantUML to use its built-in Smetana layout engine (pure Java) instead of requiring an external Graphviz `dot` binary. Without it, diagrams may fail to render in online tools (plantuml.com, kroki.io), Docker containers, and CI runners that do not have Graphviz installed. This pragma is required for **every** diagram type -- class, component, deployment, state, ER, use case, object, timing, network, ArchiMate, and nwdiag. Sequence and activity diagrams already use PlantUML's native renderer, but include the pragma anyway for consistency.

2. **ALWAYS include the Guidewire theme.**
   Every diagram must include `!include ../guidewire-theme.puml` (adjust relative path by depth). This is the single source of truth for colors, fonts, and skinparam settings. Never hardcode Guidewire palette colors directly in diagrams -- use the theme.

3. **NEVER rely on Graphviz `dot`.**
   Do not use `!pragma graphviz_dot` or any directive that assumes Graphviz is available. Do not use Graphviz-only layout features. The Smetana engine is the standard.

4. **For C4 diagrams: C4 library first, then pragma, then theme.**
   Include the C4 library **before** the theme. The theme auto-detects C4 and applies Guidewire element style overrides -- do NOT duplicate `UpdateElementStyle` calls in individual diagrams:
   ```plantuml
   @startuml diagram-name
   !pragma layout smetana
   !include <C4/C4_Context>
   !include ../guidewire-theme.puml
   ```

5. **For non-C4 diagrams: pragma first, then theme.**
   The correct preamble order is:
   ```plantuml
   @startuml diagram-name
   !pragma layout smetana
   !include ../guidewire-theme.puml
   ```

## Operating Modes

The skill detects which mode to use from the user's intent.

| Mode | Trigger Phrases | Behavior |
|------|----------------|----------|

| Single Diagram | "create a {type} diagram for {scope}", "generate sequence diagram for {flow}", "add a deployment diagram" | Generate one specific diagram type |

If the user's intent is ambiguous, ask a brief clarifying question: "Would you like me to analyze the full codebase and recommend diagrams, or generate a specific diagram type?"

## Mode: Full Analysis

### Phase 1: Codebase Scan

Scan the project to understand its architecture. Use Glob and Grep to identify:

1. **Project structure**: Glob for build files (package.json, go.mod, build.gradle, pom.xml, Cargo.toml, pyproject.toml, *.csproj) to detect language and monorepo structure
2. **Classes and types**: Grep for class/interface/struct/type definitions
3. **Services and APIs**: Grep for REST controllers, route handlers, gRPC services, GraphQL resolvers
4. **State machines**: Grep for state/transition patterns, FSM libraries, status enums
5. **Database schemas**: Grep for migration files, ORM models, entity annotations, SQL DDL
6. **Configuration**: Read deployment manifests (Dockerfile, docker-compose.yml, k8s YAML, terraform files)

**Monorepo detection**: If multiple build files exist at distinct directory levels (e.g., `services/auth/package.json` and `services/billing/package.json`), or if Nx/Lerna/Turborepo workspace config is found, treat as monorepo. Record the module names.

**Minimal codebase check**: If the scan finds no classes, services, or meaningful modules, report: "Not enough codebase structure to recommend architecture diagrams. Consider running again after establishing core modules." Do not generate empty diagrams.

### Phase 2: Recommend Diagrams

Produce a prioritized list of recommended diagrams organized into tiers:

**Tier 1 -- Core (always recommended):**
- Component overview (C4 System Context) -- shows the system in its environment
- Class domain model -- shows key domain entities and relationships

**Tier 2 -- Recommended (if relevant patterns found):**
- Sequence diagrams for the top 3-5 critical flows (auth, core business operations, API interactions)
- Deployment diagram (if infrastructure config found)
- ER diagram (if database schemas/ORM models found)

**Tier 3 -- Optional (only if specific patterns detected):**
- State diagrams (if state machines or lifecycle patterns found)
- Activity diagrams (if workflow/pipeline patterns found)
- Timing diagrams (if temporal behavior is critical)
- Use case diagrams (if user-facing capability boundaries are clear)
- Object diagrams (if runtime configuration snapshots are useful)

For each recommendation include: diagram type, proposed name, brief description, and the source files it will document.

Present recommendations to the user and ask for approval.

### Phase 3: Tiered Generation

Generate diagrams tier by tier with user checkpoints:

1. **Setup**: Read or create `docs/architecture/guidewire-theme.puml`, `docs/architecture/build.sh`, and `docs/architecture/.gitignore` (copy from templates if missing; for `.gitignore`, copy from `templates/gitignore`; make `build.sh` executable). Read or create `docs/architecture/manifest.yaml`.
2. **Generate Tier 1**: For each approved Tier 1 diagram, execute the diagram generation process (see "Generating a Diagram" below).
3. **Checkpoint**: Present Tier 1 results. Ask: "Tier 1 diagrams generated. Continue to Tier 2 (sequence flows, deployment, ER)?"
4. **Generate Tier 2**: If approved, generate Tier 2 diagrams.
5. **Checkpoint**: Present Tier 2 results. Ask: "Continue to Tier 3 (state, activity, timing, use case, object)?"
6. **Generate Tier 3**: If approved, generate Tier 3 diagrams.
7. **Summary**: Report all generated diagrams with their paths.

## Mode: Single Diagram

1. Identify the requested diagram type and scope from the user's message.
2. Read the relevant source files for the requested scope.
3. Check `docs/architecture/manifest.yaml` for an existing diagram:
   - **Exists**: Read the existing `.puml` file, apply incremental modifications, update the manifest entry.
   - **New**: Execute the diagram generation process, add a manifest entry.
4. Report what was created or updated.

## Mode: Status Report

This mode is **read-only** -- do not write any files.

1. Read `docs/architecture/manifest.yaml`. If missing, report: "No architecture docs found at docs/architecture/. Run full analysis first."
2. For each manifest entry:
   - Check if source files still exist (mark `deprecated` if not)
   - Compare source file modification times against the diagram's `updated` date (mark `stale` if source is newer)
3. Scan the codebase for undocumented areas (modules, services, or schemas not covered by any diagram).
4. Produce a coverage report:
   - Documented diagrams grouped by type, showing name, description, last updated, status (current/stale/deprecated)
   - Stale diagrams with the specific source files that changed
   - Recommended new diagrams for undocumented areas

## Mode: Update

1. Read `docs/architecture/manifest.yaml`. Identify stale diagrams.
2. For each stale diagram:
   a. Read the existing `.puml` file
   b. Read the current state of its source files
   c. Determine if an incremental update is feasible (changes affect <50% of diagram elements) or if full regeneration is needed
   d. Apply changes:
      - **Incremental**: Modify specific elements (add/remove classes, update relationships, add participants). Preserve manual annotations, notes, and layout customizations. Preserve custom override blocks.
      - **Full regeneration**: Regenerate from scratch. Notify the user that manual annotations could not be preserved.
   e. Update the header comment block timestamps
   f. Update the manifest entry (updated date, source file list, status -> current)
3. Report what was updated.

## Generating a Diagram

This process applies to every diagram regardless of mode.

### Step 1: Analyze Source Files

Read the source files identified for this diagram. Extract the architectural elements relevant to the diagram type (see "Per-Type Generation Guidelines" below).

### Step 2: Check Complexity

Count the primary elements (classes, participants, components, entities, states, etc.). If the count exceeds the threshold for this type, decompose:

| Diagram Type | Threshold | Decomposition Strategy |
|-------------|-----------|----------------------|
| Class | >20 classes | Split by package/namespace |
| Sequence | >15 participants | Split by subsystem interaction |
| Component | >12 components | Split by architectural layer |
| ER | >15 entities | Split by domain/schema |
| Deployment | >10 nodes | Split by environment or tier |
| State | >12 states | Split by composite state |
| Activity | >15 actions | Split by swim lane |

When decomposing:
- Create `<name>-overview.puml` showing high-level groupings
- Create `<name>-<subsystem>.puml` for each detail group
- Add a legend to the overview linking to detail files
- Add a note in each detail file linking back to the overview

If below threshold, generate as a single file.

### Step 3: Generate PlantUML Code

Follow these quality rules for every diagram:

1. Begin with the header comment block:
```
' ==============================================
' Generated by: diagrams skill
' Diagram:      <diagram-name>
' Type:         <diagram-type>
' Sources:      <source-file-1>,
'               <source-file-2>
' Created:      <YYYY-MM-DD>
' Updated:      <YYYY-MM-DD>
' ==============================================
```

2. Start with `@startuml <diagram-name>` (kebab-case)
3. **Add `!pragma layout smetana` and theme include** -- follow the exact preamble order specified in CRITICAL RULES above (rule #4 for C4, rule #5 for non-C4)
4. Add `title <Diagram Purpose>`
5. Declare all elements explicitly at the top before any relationships/interactions
6. For detailed sequence diagrams, add `autonumber` after participant declarations
7. Ensure every `activate` has a matching `deactivate`, every fragment has a matching `end`
8. Add a `legend` block when using non-obvious conventions, abbreviations, or custom colors
9. End with `@enduml`
**Rendering safety rules (apply to ALL diagram types, not just sequence):**

These rules prevent "Illegal sequence arrow", "No valid diagram found", and silent rendering failures. They apply globally -- to sequence, state, activity, component, deployment, class, and all other diagram types.

**Global text rules (all diagram types):**

10. **Never use angle brackets in any text.** PlantUML interprets `<` and `>` as HTML/markup tokens, which corrupts the parser and causes cascading errors (often reported on a different line). Use curly braces instead: `"Analyzing: {filename}"` not `"Analyzing: <filename>"`. This applies to all labels, descriptions, notes, state descriptions, and transition labels across every diagram type.
11. **Never use double-dashes (`--`) in any text.** Double-dashes are PlantUML syntax (composite state separators, note separators, relationship arrows). In labels, they cause parse failures. Instead of `--file`, write `file flag`. Instead of `--skip-approval`, write `approval skipped`. Instead of `error / timeout`, write `error or timeout`.
12. **Never use CLI flags or code literals in labels.** Flags like `--verbose`, filenames like `.spec.ts`, operators like `!`, `||`, `>=`, and code like `entry / action` are all problematic. Translate to plain English: `--verbose` -> `verbose mode`, `.spec.ts` -> `test specs`, `!--skip-approval` -> `approval not skipped`, `coverage >= threshold` -> `coverage met`, `entry / present plan` -> `Present plan to user`.
13. **Use slashes only in arrows, never as word separators.** PlantUML reserves `/` for arrow syntax and state actions. Instead of `error / timeout` or `source not found / access denied`, write `error or timeout` or `source not found`.
14. **Keep all display names and labels as plain English.** No parentheses, square brackets, pipes, nested quotes, asterisks, dots, equals signs, or special characters in any label -- whether it is a participant name, state name, transition label, artifact name, or note. **Square brackets are especially dangerous** -- PlantUML interprets `[text]` as creole strikethrough markup, rendering it with a line through the middle. Never use `[--flag]` or `[optional]` syntax in labels. Put technical details in a separate `note` block instead. Also never use `function()` call syntax in arrow labels -- `run(flags)` renders the parenthesized content oddly. Write `run with flags` instead.

**Sequence diagram rules:**

15. **Use `->` (solid) for forward/error messages, `-->` (dashed) only for returns.** Inside `alt`/`opt`/`loop` fragments, do not use `-->` for messages that flow toward the originating actor. Use `->` for forward flow and `-->` only for explicit return responses to a prior call.
16. **Avoid special characters and keywords in fragment labels.** Keep `alt`/`opt`/`loop`/`break`/`critical` labels as plain text. Parenthesized lists are especially dangerous -- `loop for each element (input, button, select)` will fail because `select` is a PlantUML keyword. Use plain English and put details in a note.
17. **Place notes outside fragment blocks.** Do not put `note right of` / `note left of` inside `loop`, `alt`, `opt`, or other fragments -- smetana layout fails silently, producing "No valid diagram found." Place notes immediately after the fragment's `end`.
18. **Keep participant display names simple.** Do not use parentheses or `\n` with parentheses in participant labels. Instead of `participant "CLI\n(oclif)" as cli`, use `participant "CLI" as cli`.

**State diagram rules:**

19. **Avoid composite (nested) states with smetana layout.** Composite states (`state "Name" { ... }`) with multiple `[*]` entries or nested sub-states frequently fail to render with `!pragma layout smetana`. Prefer flat state diagrams -- represent sub-processes as sequential states rather than nested composites. If grouping is needed, use `state "Name" as alias` with plain transitions between them.
20. **Do not use UML state entry/exit syntax.** `entry / action` and `exit / action` syntax uses the slash character which conflicts with smetana. Instead, write the action directly in the state description: `StateName : Present plan to user` not `StateName : entry / present plan`.
21. **Never use `== ... ==` separators in state diagrams.** The `== Label ==` syntax is a sequence diagram divider -- it causes a syntax error in state diagrams. To visually separate sections in a state diagram, use comments (`' --- Section ---`) or group related states inside a single-level composite state (`state "Group Label" as grp { ... }`). If multiple `[*]` initial states are needed (e.g., showing independent state machines), each must be inside its own composite state block.

**Component diagram rules:**

22. **Never use dots in component display names.** PlantUML interprets dots as namespace separators, which corrupts the parser. Instead of `component "main.py" as main`, write `component "main" as main`. File extensions, version numbers, and any dotted notation must be stripped from display names. If the extension is important context, add it as a note or stereotype instead.
23. **Keep component diagrams under 20 components with smetana.** Smetana layout silently fails ("No valid diagram found") when the combination of components and relationships exceeds its layout capacity. If a component diagram exceeds 20 components, either decompose into overview + detail diagrams (per the complexity threshold rules), or remove relationship labels to reduce layout pressure. Unlabeled arrows (`A --> B`) render more reliably than labeled ones (`A --> B : long description`) at high density.

If the user has requested custom styling, insert overrides in a delimited block:
```plantuml
' --- Custom overrides (user or skill-applied) ---
skinparam participant {
  BackgroundColor #E0FFE0
}
' --- End custom overrides ---
```

### Step 4: Write File

1. Create the type subdirectory if it does not exist (e.g., `docs/architecture/sequence/`)
2. Write the `.puml` file using kebab-case filename
3. For monorepo mode, write under `docs/architecture/<module>/<type>/`

### Step 5: Update Manifest

Add or update the entry in `docs/architecture/manifest.yaml`:

```yaml
- name: <diagram-name>
  type: <diagram-type>
  path: <type>/<diagram-name>.puml
  description: "<brief description>"
  module: null  # or module name for monorepo
  sources:
    - <source-file-1>
    - <source-file-2>
  decomposed: false  # true if split
  detail_files: []   # paths if decomposed
  created: "<YYYY-MM-DD>"
  updated: "<YYYY-MM-DD>"
  status: current
```

## Per-Type Generation Guidelines

### Class Diagram

**What to scan**: Class/interface/struct definitions, inheritance, composition, association, dependency relationships.

**PlantUML patterns**:
- `class ClassName { }` with `+public`, `-private`, `#protected`, `~package` visibility
- `interface InterfaceName { }`
- `abstract class AbstractName { }`
- `enum EnumName { }`
- Relationships: `--|>` (inheritance), `..|>` (implements), `*--` (composition), `o--` (aggregation), `-->` (association), `..>` (dependency)
- Group with `package "Name" { }` or `namespace Name { }`

**Complexity threshold**: >20 classes -> decompose by package/namespace.

Refer to `references/class.md` for complete syntax.

### Object Diagram

**What to scan**: Configuration objects, test fixtures, runtime state snapshots.

**PlantUML patterns**:
- `object "Name" as alias { field = value }`
- Links: `alias --> alias`

Refer to `references/object.md` for complete syntax.

### Component Diagram (including C4)

**What to scan**: Modules, packages, service boundaries, provided/required interfaces.

**For C4 System Context (Tier 1 core)**:
- Use `!include <C4/C4_Context>` with Guidewire theme overrides
- `Person(alias, "Name", "Description")`
- `System(alias, "Name", "Description")`
- `System_Ext(alias, "Name", "Description")`
- `Rel(from, to, "Label", "Protocol")`

**For C4 Container**:
- Use `!include <C4/C4_Container>`
- `Container(alias, "Name", "Technology", "Description")`
- `ContainerDb(alias, "Name", "Technology", "Description")`
- `ContainerQueue(alias, "Name", "Technology", "Description")`

**For standard component diagrams**:
- `component "Name" as alias`
- `interface "Name" as alias`
- `[Component] --> [Other]`
- Group with `package "Layer" { }`

**Complexity threshold**: >12 components -> decompose by architectural layer.

Refer to `references/component.md` for complete syntax.

### Deployment Diagram

**What to scan**: Dockerfiles, docker-compose.yml, Kubernetes manifests, Terraform files, CI/CD configs.

**PlantUML patterns**:
- `node "Name" { }` for servers/VMs
- `database "Name"` for data stores
- `cloud "Name" { }` for cloud providers
- `artifact "Name"` for deployable units
- Communication: `node1 --> node2 : protocol`

**Complexity threshold**: >10 nodes -> decompose by environment or tier.

Refer to `references/deployment.md` for complete syntax.

### Sequence Diagram

**What to scan**: API endpoint handlers, service-to-service calls, message flows, event handlers.

**PlantUML patterns**:
- Participant types: `actor`, `participant`, `boundary`, `control`, `entity`, `database`, `collections`, `queue`
- Arrows: `->` (sync), `->>` (async), `-->` (return), `->x` (lost)
- Activation: `activate Participant` / `deactivate Participant` (or `++` / `--`)
- Fragments: `alt/else/end`, `opt/end`, `loop/end`, `par/end`, `break/end`, `critical/end`
- `autonumber` for detailed level
- Group participants with `box "Name" #Color ... end box`
- Dividers: `== Phase Name ==`

**Complexity threshold**: >15 participants -> decompose by subsystem interaction.

Refer to `references/sequence.md` for complete syntax.

### Activity Diagram (New Syntax Only)

**What to scan**: Workflows, pipelines, business processes, CI/CD flows.

**PlantUML patterns** (new syntax only, not legacy):
- `start` / `stop` / `end`
- `:Action;` for activities
- `if (condition?) then (yes)` / `else (no)` / `endif`
- `fork` / `fork again` / `end fork` for parallel
- `|Swimlane|` for responsibility partitioning
- `partition "Name" { }` for grouping
- `repeat` / `repeat while (condition?)`

**Complexity threshold**: >15 actions -> decompose by swim lane.

Refer to `references/activity.md` for complete syntax.

### State Diagram

**What to scan**: Enum-based states, FSM implementations, lifecycle patterns, status fields with transitions.

**PlantUML patterns**:
- `[*] --> StateName` (initial), `StateName --> [*]` (final)
- `State1 --> State2 : event [guard] / action`
- `state StateName { }` for nested/composite states
- `state "Long Name" as alias`
- `StateName : entry / action`
- `StateName : exit / action`
- `--` for concurrent regions

**Complexity threshold**: >12 states -> decompose by composite state.

Refer to `references/state.md` for complete syntax.

### Use Case Diagram

**What to scan**: User-facing features, API endpoints grouped by actor, role-based access patterns.

**PlantUML patterns**:
- `actor "Name" as alias`
- `usecase "Name" as alias`
- `rectangle "System Boundary" { }` for system boundary
- `actor --> usecase`
- `usecase .> usecase : <<include>>`
- `usecase .> usecase : <<extend>>`

Refer to `references/use-case.md` for complete syntax.

### Timing Diagram

**What to scan**: Protocol handshakes, retry logic, circuit breaker states, time-dependent behaviors.

**PlantUML patterns**:
- `concise "Name" as alias` or `robust "Name" as alias`
- `@0 / @50 / @100` for time points
- `alias is State`
- `alias@time <-> alias@time : constraint`

Refer to `references/timing.md` for complete syntax.

### ER Diagram (Information Engineering)

**What to scan**: Database migrations, ORM model definitions, SQL DDL, entity annotations.

**PlantUML patterns**:
- `entity "Name" { * primary_key \n -- \n field_name : type }`
- Relationships with cardinality:
  - `||--o{` (one to many)
  - `||--||` (one to one)
  - `}o--o{` (many to many)
  - `||..|{` (one to many, identifying)

**Complexity threshold**: >15 entities -> decompose by domain/schema.

Refer to `references/er.md` for complete syntax.

### Network Diagram (nwdiag)

**What to scan**: Network configuration, infrastructure-as-code, deployment manifests with network settings.

**PlantUML patterns**:
- `nwdiag { }` wrapper
- `network Name { address = "x.x.x.x/y" }`
- `server "Name" { address = "x.x.x.x" }`
- Groups for logical segmentation

Refer to `references/network.md` for complete syntax.

### ArchiMate Diagram

**What to scan**: Enterprise architecture artifacts, business process documentation, application landscape.

**PlantUML patterns**:
- Business layer: `Business_Process`, `Business_Actor`, `Business_Role`, `Business_Service`
- Application layer: `Application_Component`, `Application_Service`, `Application_Interface`
- Technology layer: `Technology_Service`, `Node`, `Device`, `Infrastructure_Service`
- Relationships: `Rel_Composition`, `Rel_Aggregation`, `Rel_Assignment`, `Rel_Serving`, `Rel_Realization`, `Rel_Flow`, `Rel_Triggering`, `Rel_Access`

Refer to `references/archimate.md` for complete syntax.

## Portable / Online Rendering

Diagrams use `!include` for the Guidewire theme, which requires the theme file to be present locally. To produce self-contained `.puml` files suitable for online tools (plantuml.com, kroki.io, PlantText, etc.), run the build script:

```bash
./docs/architecture/build.sh
```

This inlines all relative `!include` directives, replacing them with the actual file contents. Output goes to `docs/architecture/.build/` mirroring the source directory structure. The `.build/` directory is git-ignored.

To build a single file:

```bash
./docs/architecture/build.sh component/system-context.puml
```

When a user asks about sharing diagrams online, rendering in a browser tool, or getting a portable version, point them to this build script.

## Error Handling

| Scenario | Response |
|----------|----------|
| Minimal/empty codebase | Report "insufficient structure"; suggest running after more code |
| manifest.yaml missing (update/status) | Report "no architecture docs found"; suggest full analysis |
| manifest.yaml malformed | Report error; offer to regenerate from existing .puml files |
| Source file no longer exists | Mark diagram `deprecated` in manifest; notify user |
| Theme file missing | Copy from capability templates before generating |
| User rejects all recommendations | Acknowledge; suggest specific diagram type |
| Incremental update too divergent | Fall back to full regen; notify about annotation loss |
| Monorepo boundaries unclear | Present detected modules; ask for confirmation |
